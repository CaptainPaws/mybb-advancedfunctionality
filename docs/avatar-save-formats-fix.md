# UserCP: исправление сохранения, Gallery и форматов

## 1. JPG и сообщение об отсутствии подтверждения

Разбор начат с неизменённого MyBB 1.8.40: do_avatar принимает avatarupload, проверяет CSRF/группу, вызывает upload_avatar(), обновляет users, затем вызывает usercp_do_avatar_end и redirect(). Штатный redirect() может вернуть Location, HTML-шаблон или AJAX JSON с JavaScript внутри data. Формат ответа также зависит от настроек и шаблона форума.

Предыдущий runtime не ожидал JSON как единственный контракт: он пытался найти в HTML новую карточку либо точный meta-refresh на avatar. Если их не было, выводил «Сервер не подтвердил сохранение». Это означало отсутствие распознанного UI/редиректа, а не доказанный отказ записи. Сценарий сохранённого аватара с другим HTML/JS ответом давал ложную ошибку. Сам путь multipart обычного JPG в исходнике корректен. Без сетевого ответа/логов рабочего сайта невозможно честно утверждать, что там файл вообще не записывался или назвать конкретный шаблон, вызвавший сбой.

Теперь native usercp_do_avatar_end формирует подтверждение только после штатного обновления users и повторного чтения записи. Проверяется совпадение с реально записанным native updated_avatar, а для upload — доступность настоящего файла. APF аналогично подтверждает только после собственного setter и чтения profile_secondary_avatar. Это не фиктивный JSON и не замена обработчика: подтверждение до записи или при несовпадении отклоняется.

Клиент использует исходное состояние из серверной разметки карточки либо последнее подтверждённое состояние; предварительный GET не блокирует POST. Подтверждение включает UID, роль, URL, размеры, MIME и версию, учитывающую содержимое локального файла. Если вместо него получен старый/custom HTML, JavaScript или стандартный MyBB data, выполняется только чтение состояния через GET action=af_avatar_state. Изменение проверенного состояния подтверждает результат; отсутствие изменения даёт отдельную диагностику, не фиктивный успех. Повторного POST нет, скрипты из ответа не исполняются. JSON errors и HTML-ошибки показываются отдельно и сохраняют выбранный файл/preview. Одинаковый файл, повторно сохранённый с действующим новым подтверждением, также подтверждается успешно, даже если его версия не изменилась.

Read-only state использует текущего авторизованного пользователя и прежние users/APF, проверяет CSRF, не принимает чужой UID, не создаёт новое хранилище. Нативные способы без async-флага сохраняют прежний контракт.

## 2. Unknown Gallery purpose

В текущем main правильные account_avatar/character_avatar уже присутствовали и в PHP, и в JS; новая карточка передавала их правильно. Владелец assets при этом удалял ?v= и всегда подключал advancedgallery.js по одному URL. Это позволяло после обновления оставить старый JS со старым whitelist и получить Unknown Gallery purpose. Точную установленную на сайте копию без browser/network log не проверяли; устаревший runtime/неполная установка — совместимое с найденным дефектом объяснение.

Удалено снятие версии; CSS/JS получают content revision из SHA-256 файла. В конфиг Picker передаются разрешённые purposes существующего PHP-реестра. Валидация остаётся строгой; не применяется преобразование произвольного gallery в системное назначение. Runtime объявляет supportsPurpose, а UserCP проверяет совместимость и показывает конкретную диагностику при старом/недоступном Picker. Открытие, picker_data, миниатюры, picker_select, ag_avatar_source и последующий save продолжают использовать одну выбранную роль. Второго Picker нет.

## 3. Кто сохраняет

- Основной: тот же MyBB do_avatar -> upload_avatar() -> users.avatar/avatardimensions/avatartype. GIF/JPG/PNG не перекодируются без необходимости. Реальная запись проверена через исходный блок do_avatar, а не только функцию генерации файла.
- Дополнительный: прежний AdvancedProfileFields do_apf_secondary_avatar -> af_apf_validate_secondary_avatar_upload() -> move_uploaded_file()/af_apf_set_system_value(). Путь и таблица af_apf_values/profile_secondary_avatar не менялись. AdvancedProfileUI и публичные провайдеры не изменены.

## 4. WebP и общий источник возможностей

Штатный MyBB 1.8.40 жёстко ограничивает расширения и MIME внутри upload_avatar(): одного avatarfile=Да в ACP недостаточно для WebP. Новый общий Core helper af_avatar_capabilities() используется UI (accept, labels и JSON клиентских лимитов), Gallery и серверной обработкой. Для APF серверная валидация также читает этот источник. Порядок обычных форматов: JPG, PNG, WebP, GIF — с учётом реальных разрешений; отключённые в ACP типы основного аватара не рекламируются.

Для основного WebP hook после проверки Gallery/прав/CSRF проверяет фактический IMAGETYPE_WEBP, исходный лимит ACP и avatarsize, размеры, политику уменьшения и доступную обработку. GD действительно декодирует WebP и создаёт отдельную PNG-копию с альфой; если PNG запрещён, допускается разрешённый JPG. Изменяется только настоящий multipart temp: новая копия передаётся native upload_avatar с достоверным MIME/расширением и размером. PHP is_uploaded_file() остаётся настоящим. Native повторно проверяет конечный тип/лимиты/размеры, управляет avataruploadpath, CDN и удалением предыдущих файлов. Отдельного каталога/поля основного аватара нет. Gallery hash/ownership проверяется до преобразования; исходник Gallery остаётся WebP с прежним SHA-256.

Условия WebP основного аватара: разрешённый для группы ACP WebP, GD с WebP-декодером, разрешённый PNG или JPG как конечная копия. Без этих условий UI не обещает рабочий WebP, показывает причину; требуется исправить конфигурацию сервера/типов, а не подменять MIME. Для безопасного декодирования ограничивается число пикселей и проверяется память. Конечная PNG/JPG-копия также должна укладываться в ограничения MyBB.

Дополнительный APF уже принимает настоящий WebP и сохраняет оригинальные байты; преобразование ему не требуется.

## 5. Анимация

GIF в допустимых размерах сохраняется побайтно, включая анимацию. Прежний guard основного GIF, требующего уменьшения, сохраняет понятный отказ вместо молчаливой потери кадров. APF не уменьшает GIF и сохраняет его как есть. Анимированный WebP для основного отклоняется: преобразование в статичный PNG/JPG было бы потерей анимации. APF сохраняет и анимированный WebP без изменения байтов.

## 6. Проверки и границы

Проверки короткие, на PHP 8.5 с настоящим GD/WebP. Сначала пройден JPG через upstream MyBB 1.8.40 do_avatar -> users update -> read-back receipt, затем добавлены форматы. Проверены JPG/PNG/анимированный GIF/WebP основного и APF, оба назначения Gallery, подмена UID, CSRF, права/MIME/размер, несовпадение подтверждения с БД, неизменность SHA-256 Gallery и настоящий MIME сохранённой PNG. Анимация GIF/APF WebP подтверждена совпадением хешей, а не расширением. Fixture использует изолированные /tmp файлы и fake DB с реальными owning handlers; не запускать её на production.

Короткий локальный Chromium-проверочный сценарий прошёл для штатной модалки обоих контекстов, FormData, upload/URL, серверных ошибок, read-back JSON, успешного custom HTML без meta-refresh, неоднозначного ответа без записи и отсутствия повторного POST. Проверены действующее версионирование assets и передача PHP purpose registry. PHP/JS syntax и git diff --check пройдены. UI/CSS и внешняя навигация не переделывались. Полный визуальный сценарий и установленная конфигурация сайта остаются заказчику.

### Восстановление общего runtime и маршрут состояния

Core при установке и реактивации вызывает `af_ensure_avatar_runtime()` до
обнаружения аддонов. Встроенный в `advancedfunctionality.php` исходник должен
побайтово совпадать с `advancedfunctionality/avatar.php` (проверяется
`tests/avatar_runtime_install_regression.php`). Отсутствующий или отличающийся
файл заменяется атомарно; актуальный файл не переписывается. Сетевой загрузки
PHP нет, ошибки прав записи сообщаются явно, OPcache инвалидируется.

Новый запрос состояния использует штатный адрес
`usercp.php?action=avatar&af_avatar_state=1`, а Core заранее регистрирует
обработчик `usercp_start`. Прежний `action=af_avatar_state` оставлен совместимым
на сервере. Проверки текущего пользователя, доступа UserCP и CSRF сохранены.
HTTP 404 до POST блокировал все источники изображений одинаково; без доступа
к конфигурации production нельзя установить, какой именно серверный фильтр
или версия установленного обработчика возвращала этот статус.

Для обновления необходимо загрузить изменённые файлы Core и ATF и
деактивировать/активировать **Advanced functionality**. При отсутствии
общего `avatar.php` реактивация создаст его из встроенного исходника.

### Hotfix: точная причина HTTP 404 после 934a32a2

В обеих формах есть `<input name="action">`. В браузере такой элемент
перекрывает свойство `form.action`: вместо строки URL оно возвращает
`HTMLInputElement`. В результате `new URL(form.action, location.href)`
создавал путь `/[object%20HTMLInputElement]`, а не `/usercp.php`.
Запрос не достигал PHP-маршрута AF. Изменение query-параметров в 934a32a2
не устраняло эту причину; предположение о серверной фильтрации было неверным.

Runtime теперь получает единый адрес GET/POST через
`new URL(form.getAttribute('action'), document.baseURI)`. Назначение
`action=avatar&af_avatar_state=1`, роли и CSRF сохранены. PHP, UI и
механизм установки runtime в этом hotfix не меняются. Ошибки проверки до
POST и после неоднозначного ответа POST различаются; повторной отправки нет.

Короткий браузерный тест проверяет точный pathname `/usercp.php`, метод,
обе роли, CSRF, сохранение и удаление обоих аватаров. Любой другой путь
возвращает 404. Предыдущий тест ошибочно принимал запросы состояния по одним
query-параметрам и поэтому пропускал дефект пути. Production-сессия в тесте
не используется; исправление подтверждено воспроизведением DOM-конфликта
в Chromium и строгим локальным контролем фактических URL запросов.


### Hotfix: HTTP 200 с JSON и дописанным HTML

Фактический ответ заказчика начинается корректным JSON состояния, после
которого следуют `af_advancedfontawesome_done`, `af_advancedmenu_applied`,
CSS/JS и `af_core_preoutput_done`. Это подтверждает выполнение маршрута.
Причина в shutdown-обработчике `advancedfunctionality_outputbuffer_flush()`:
AF стартует буфер на `global_start` для UserCP, а при `exit` из JSON-handler
обрабатывает буфер через HTML providers. Проверка `af_should_skip_preoutput()`
учитывала `ajax`, Accept и специальный флаг, но JSON-helper не устанавливал
флаг, а запрос fetch не объявлял JSON. Сам Content-Type ответа игнорировался.
В результате валидный JSON превращался в невалидное тело JSON + HTML.
Предположение о старом runtime не является причиной присланного ответа.

Исправление:

- `af_avatar_json()` выставляет существующий `af_disable_pre_output` до вывода
  и `exit`; встроенная установочная копия в Core обновлена синхронно.
- Core также пропускает HTML-фильтры для фактического Content-Type
  `application/json` и `application/*+json`, включая старые helpers без флага.
- GET состояния передаёт `Accept: application/json`.
- POST не требует предварительного GET: используется `data-avatar-version`
  из серверной карточки/последнего подтверждения. JSON receipt подтверждает
  сохранение; после неоднозначного HTML используется только GET состояния.
  Ошибка этой проверки не объявляется отказом сохранения; выбор остаётся
  в интерфейсе. Автоматического повторного POST нет.

Проверены PHP 8.5, JS-синтаксис, восстановление runtime, обе роли и POST receipt
с реально включённым Core shutdown-буфером. Локальная HTTP-проверка использует
штатные MyBB 1.8.40 `pluginSystem`, `get_input` и `verify_post_check`, тестовые
сессию/БД: обе роли возвращают полностью разбираемый JSON, включая отсутствие
аватара персонажа. Отдельно проверен старый JSON-helper без нового флага —
его защищает Content-Type. Короткий browser regression проверяет отсутствие
предварительного GET, сохранение при недоступном GET и безопасную обработку
HTTP 200 JSON + HTML после неоднозначного POST. UI, права, CSRF, загрузчики,
хранение, MIME и обработка GIF/WebP не менялись.

Обновление: загрузить Core, JS редактора и общий `avatar.php`, затем
реактивировать **Advanced functionality** (это также восстановит общий
runtime из Core). При настроенном OPcache без проверки timestamps требуется
сброс OPcache или перезапуск PHP-FPM для обновлённого Core. Обновить страницу
редактора с очисткой браузерного кеша.
