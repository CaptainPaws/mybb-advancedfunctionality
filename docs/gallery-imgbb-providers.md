# AdvancedGallery 1.2: ImgBB и провайдеры хранения

## Включение

1. Загрузить исходники и реактивировать AdvancedGallery. Миграция добавляет две таблицы; существующие локальные записи не переписываются.
2. В ACP → AdvancedFunctionality → AdvancedGallery → **Внешние хранилища** задать ключ ImgBB, включить провайдер, размер файла, группы, разрешение загрузки по URL и выбор ImgBB по умолчанию.
3. В Gallery → Загрузить выбрать **Место хранения → ImgBB**, затем файл или прямую ссылку. Такой же выбор доступен в Picker.

ImgBB требует PHP cURL, fileinfo, доступ к HTTPS API и временный каталог PHP. Максимум API ограничен 32 000 000 байтами; настройка Gallery дополнительно уменьшает его. Ограничения PHP `upload_max_filesize`/`post_max_size` также действуют. Внешние оригиналы не расходуют локальную объёмную квоту и не копируются в `uploads/af_gallery`.

Локальная загрузка остаётся прежним обработчиком `ag_handle_local_upload`, вызываемым адаптером `local`. Если поле `storage_provider` отсутствует, используется local. Клиент не может включить отключённый провайдер или обойти группы. Учитываются право загрузки Gallery, собственный переключатель ImgBB и основная/дополнительные группы MyBB.

## Приватные и публичные данные

- В `af_gallery_media` сохраняются существующие поля: владелец, тип remote, provider=imgbb, оригинальный URL, thumbnail, исходный размер, MIME/расширение, ширина/высота, original_name, даты и approved/pending/rejected.
- `af_gallery_external_media`: media_id, внешний ID, viewer URL, **служебный delete URL**, availability и время загрузки. Связь с альбомом — существующая `af_gallery_album_media`.
- `af_gallery_provider_secrets`: серверный API-ключ. Он не регистрируется как обычная настройка MyBB, не попадает в `inc/settings.php`, JS, пользовательский HTML, публичный JSON или URL браузера. Только в административном ACP текущий ключ показан маской с последними четырьмя символами и может быть полностью раскрыт через «Показать сохранённый ключ». Поле для замены всегда пустое: пустая отправка сохраняет ключ, отдельный переключатель удаляет его. Ключ хранится в серверной БД; доступ к БД и резервным копиям должен оставаться административным.

Служебный delete URL нигде не выводится, включая ACP. Публичные ответы формируются явным перечнем полей и не сериализуют приватную таблицу. Ключ показывается только в административной форме, служебный delete URL — нигде. Текст ошибки API не возвращается клиенту: он может содержать служебные данные.

Для владельца автоматически создаётся приватный системный альбом `provider_imgbb` с названием «ImgBB». Переименование не меняет идентификатор. Он не входит в лимит обычных альбомов. UID берётся только из сессии, а не из POST. Обычный пользователь не может читать или выбирать чужие записи. Администратор просматривает загруженные внешние записи на странице ACP (по 50, без HTTP-проверок).

Все новые загрузки отправляются в служебный альбом своего провайдера. После загрузки изображение можно перенести в пользовательский альбом существующим механизмом, без скачивания на сервер. При перемещении в публичный пользовательский альбом действуют существующие правила публикации Gallery. Служебный альбом провайдера не принимает локальные файлы или файлы другого хостинга.

Приватность каталога Gallery не делает URL ImgBB закрытым: любой обладатель прямой ссылки может открыть изображение на хостинге. Перед загрузкой форма сообщает о публичности внешнего URL.

## Запросы и временные файлы

Официальный API: [ImgBB API v1](https://api.imgbb.com/). Используется только `POST https://api.imgbb.com/1/upload`, multipart `key` + `image`. Ключ находится в теле серверного запроса. `expiration` не отправляется. TLS проверяется, перенаправления API запрещены, время и размер ответа ограничены.

Для файла с устройства проверяются `is_uploaded_file`, реальный размер, fileinfo и getimagesize. Для URL сервер сначала скачивает ограниченный временный файл и проверяет его тем же способом; исходный URL не передаётся ImgBB как непроверенная команда загрузки. В обоих случаях постоянная локальная копия не создаётся, временный файл удаляется при успехе/ошибке. Для скачанных оригиналов также зарегистрирована очистка при завершении запроса.

HTTP-статус, корректный JSON, success/status, идентификатор, MIME, размеры и URL ответа проверяются. Оригиналы и превью ImgBB принимаются только по HTTPS с `i.ibb.co`; viewer/delete URL — с `ibb.co`. Транзакция сохраняет только метаданные и связи. Если API принял изображение, а БД не смогла сохранить запись, интерфейс честно сообщает, что удаление на внешнем хостинге не подтверждено; автоматической повторной отправки или удаления нет.

### SSRF

Разрешены только HTTP/HTTPS, стандартные порты, без userinfo, управляющих символов, обратного слеша и fragment. Проверяются все A/AAAA-адреса: внутренние, link-local, loopback, CGNAT, зарезервированные диапазоны и IPv6-переходные адреса отклоняются. Публичный адрес закрепляется через CURLOPT_RESOLVE, после соединения проверяется реальный IP. Перенаправления не поддерживаются. Размер ограничен и по объявленной длине, и потоковым счётчиком байтов, с timeout.

Если среда задаёт HTTP(S)/ALL forward proxy, URL-загрузка и серверное получение внешнего оригинала для аватара отклоняются: такой прокси может самостоятельно разрешить DNS и обойти закреплённый IP. Прокси не обходится. Загрузка **с устройства на фиксированный API ImgBB** при этом доступна. Для URL/аватаров требуется среда, позволяющая гарантировать прямое DNS-pinned соединение. При запрете URL настройкой сервер также отклоняет URL независимо от JS.

## Совместимость и аватары

ImgBB-изображения участвуют в Gallery Picker, BBCode, ссылках, публикации и модерации. В начальную группу аватаров добавляется служебный альбом внешнего провайдера; остальные альбомы остаются доступны. Pending/rejected не попадают в выборку для назначения. Механизм удержания используемых изображений оформления сохранён.

Для основного и дополнительного аватаров поддержанный провайдер временно получает оригинал с проверенного сервером URL. Приватный `avatar_original` отдаёт его владельцу с того же origin и `no-store`; браузер передаёт байты в прежнее multipart-поле MyBB/APF. Сервер повторно проверяет владельца, публикацию, MIME/геометрию и совпадение SHA-256 полученных байтов. Клиентские URL и пути не принимаются как источник. Сохранение и удаление аватаров остаются штатными; MyBB/APF создаёт собственную копию аватара, как и раньше. Это не постоянный оригинал Gallery и не новая система аватаров.

## Удаление и доступность

У внешнего изображения доступно **«Удалить из моей галереи»**. Удаляются запись, приватные метаданные и связи с альбомами; существующая защита удерживаемых изображений сохраняется. Ответ явно сообщает, что удаление с хостинга не выполнялось.

Документация ImgBB API v1 описывает upload и возвращает delete_url, но не документирует проверенный API удаления. Поэтому автоматического обращения к delete URL и кнопки «Удалить с хостинга» нет. Explicit uninstall также удаляет только данные аддона в БД; внешние файлы он не удаляет. Deactivate/activate сохраняют записи, ключ и настройки.

Availability=`available` фиксирует успешную загрузку, а не непрерывную проверку текущего состояния. Синхронных обходов внешних изображений при открытии Gallery/ACP нет.

## Подключение нового провайдера

`providers.php` содержит интерфейс `AG_StorageProvider` (`id`, `label`, `canUpload`, `supportsUrl`, `upload`) и адаптеры local/ImgBB. PHP-расширение может вызвать `ag_register_storage_provider($provider)` после загрузки Gallery.

Для внешнего провайдера наследовать `AG_ExternalStorageProvider` и реализовать `id`, `label`, `maxBytes`, `sendFile`, `validOriginalUrl`. `sendFile` возвращает external_id, url, thumb, viewer, delete_url, mime, ext, width, height, availability. Реализация обязана проверять свой API и допустимые URL. Базовый класс обеспечивает общий приём временного файла, права, транзакцию, системный альбом, очистку и ответ. Настройки `<id>_enabled`, `<id>_groups`, `<id>_allow_url` регистрируются расширением.

Поддержка аватаров по умолчанию выключена; включать `supportsAvatar()` только после проверки источника. `downloadOriginal` можно переопределить для специфичного безопасного транспорта. Клиент не задаёт endpoint провайдера. Postimages пока не реализован: архитектура позволяет подключить его без изменения локального загрузчика и потребителей медиа. Внешнее удаление требует отдельного исследования и явной реализации; общий загрузчик не предполагает его наличия.

## Проверки

Без настоящего API-ключа, на изолированной БД `gallery_test`:

```sh
php tests/gallery_imgbb_security_regression.php
AG_TEST_DB_HOST=ag-imgbb-db php tests/gallery_imgbb_fixture.php --init
# Запустить PHP fixture-сервер на 127.0.0.1:8101 с router tests/gallery_imgbb_fixture.php
python3 tests/gallery_imgbb_http_regression.py
node tests/gallery_imgbb_browser.cjs
AG_TEST_DB_HOST=ag-imgbb-db php tests/gallery_imgbb_fixture.php --after
```

Подменяется только транспорт ответа ImgBB и получение контрольного оригинала; Gallery, multipart, SQL, проверка владельца/модерации, перенос/удаление, CSRF и проверка байтов обоих аватаров настоящие. Проверяются сохранность локальных записей и ключа при миграции/реактивации, приватные URL, ошибки API с секретом в теле, отсутствие expiration, ограничения размера/формата, SSRF и отсутствие постоянных/временных копий после запроса. Chromium проверяет реальную форму, карточку, BBCode, переключение хранилищ и avatar Picker. Настоящая загрузка в аккаунт ImgBB требует административного ключа и отдельно не выполнялась.
