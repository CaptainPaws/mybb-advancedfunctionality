# ATF-KB-ORIGIN-01 — Сброс разновидности при смене происхождения

## Причина

Форма скрывала селектор разновидности и выставляла ему `disabled`. Браузер исключал его из POST, а обработчик частичных обновлений ATF сохранял пропущенные поля. Если поле `character_origin` присутствовало в разметке с пустым значением, JavaScript также пропускал действительное происхождение из `character_race`.

После явной очистки writer ATF удаляет строку значения. Индекс CharacterSheets содержит только непустые сохранённые значения. При обновлении канона синхронизация начинала со старого профиля и переносила только непустые поля, поэтому очищенная разновидность оставалась в KB. При синхронизации оригинального персонажа в новый профиль могло попасть старое значение из анкеты, поскольку эта ветка не проверяла родительскую связь.

## Изменение

- Форма использует непустое `character_origin` с резервом на `character_race`. При первой отрисовке PHP выбирает разновидность только из связанных вариантов. При смене эффективного происхождения JavaScript сразу оставляет пустой вариант и запрашивает доступные варианты из `af_atf_kb_origin_variants`. Ответ проверяется по номеру запроса и ключу происхождения. Скрытый селектор остаётся доступным для отправки пустого значения.
- DataHandler проверяет активные определения и связь `origin_has_variant` через функции KB. При смене происхождения несовместимое сохранённое значение очищается штатным writer, даже если частичный POST пропустил поле. Посторонний или некорректный переданный ключ вызывает ошибку валидации.
- При синхронизации оригинального персонажа bridge переносит ключи и проверяет родительскую связь перед формированием `rules.character_profile`. При обновлении канона наличие активного поля в конфигурации анкеты позволяет отличить очищенное поле от поля вне анкеты. Управляемая разновидность записывается пустой, если её очистили или связь не подтверждена. Если поле отсутствует в конфигурации, существующая каноническая разновидность сохраняется, пока смена происхождения не сделает её несовместимой. Повторная синхронизация не восстанавливает очищенное значение из канонического baseline.

## CharacterSheets и ACS

CharacterSheets читает ключ разновидности из синхронизированного профиля KB. Подготовка нового боевого снимка пропускает загрузку определения разновидности, если её ключ пуст, и строит характеристики из остальных доступных источников. Изменение действует через существующую синхронизацию CharacterWorkflow. Запись уже созданных снимков в этот маршрут не входит.

## Проверки

- `git diff --check`, `php -l` и `node --check` для изменённых файлов.
- **NOT_VERIFIED на warprift.ru.** Для оригинального и канонического персонажа проверить переход с Демихумана и Бирфолка на `acs_test_origin`, пустое значение в POST, состояние темы и повторно открытой формы. Затем дважды синхронизировать KB и проверить пустую разновидность, сохранность baseline, отсутствие модификаторов Бирфолка в CharacterSheets и в новом боевом снимке. Проверить возврат к Демихуману, выбор Бирфолка и другой связанной разновидности, а также быстрые последовательные смены происхождения.
