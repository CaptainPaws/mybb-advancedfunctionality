# ACS: решения по балансу и блокеры реализации

## 1. Статус реестра

Этап C; база `d593fda56e42337c0ebeb10de57e5e942ec086b9`. Этот документ сопровождает [архитектуру Combat Resolver](ACS_COMBAT_RESOLVER_DESIGN.md). Варианты и рекомендации ниже **не утверждены автоматически**. Наличие валидного поля/AST/токена KB не утверждает его игровую семантику. Содержимое установленной БД с реальными formula_def здесь не исследовалось; примеры документации не считаются принятыми формулами.

Обозначения: **У** — правило принято в постановке этапа C; **К** — структура/параметры уже задаются KB, исполнение требует поддержки; **Н** — потребуется конкретное определение KB/связь; **Р** — нужно решение владельца правил; **А** — инженерная ответственность runtime ACS. У механики может быть несколько категорий.

## 2. Уже принятые правила

| Правило | Следствие для ACS |
|---|---|
| KB определяет механики; ACS исполняет бой; CS остаётся независимым | Боевые HP/ресурсы/статусы не записываются в CS; нет переноса Resolver в KB/ATF |
| AP настраивает мастер; обычные 3 — не константа | Бюджет фиксируется версией на ход; missing action_cost не равен 0 |
| PC, питомцы и призывы делят AP; каждый monster мастера имеет свой бюджет | Budget owner не совпадает автоматически с controller/owner |
| Один боевой пост группы игрока за раунд; сущность не действует повторно через другую группу | Уникальный group entitlement и отдельный participant round claim |
| Действия одного поста последовательны | Экипировка/эффекты первого действия влияют только на последующие |
| Оружие меняется в бою за действие; броня только в мирной сцене | Стадия сессии и equip eligibility проверяются сервером |
| Забытый старый аксессуар нельзя надеть в бою; новый сюжетный аксессуар этой сессии — за 1 AP | Нужен GM grant с происхождением; отметка клиента не подходит |
| Между боями переэкипировка без AP | Не переносить цену боевого действия на мирную сцену |
| Один durable экземпляр можно использовать в нескольких активных сессиях | Неэксклюзивные bindings; любая активная привязка запрещает продажу/передачу/уничтожение/крафт |
| Расходники резервируются глобально и списываются однократно | Item locks, quantity invariant, operation id; snapshot не доказывает доступность |
| Броски фиксируются сервером до публикации; изменение/удаление не даёт reroll | Sealed immutable prefix, ledger на право хода, не на browser draft |
| Preview не применяет урон и не списывает ресурсы | Только виртуальное состояние; сохранение бросков/резерваций отделено от применения |
| Max HP increase не лечит; при уменьшении current=min(current,new_max) | Отсечённое HP не возвращается последующим повышением |
| DoT/HoT обычно срабатывает в начале хода пострадавшего, если определение это поддерживает | Явная phase/status policy, не запуск текстовых legacy статусов |
| Начало хода — идемпотентная серверная операция | Никаких тиков по просмотру страницы |
| История после публикации неизменна | Quick Edit/текст не пересчитывают бой; corrections мастера — новые события |
| Неизвестная формула не заменяется seed или арифметикой CS | Подготовка действия отказывает с диагностикой |

## 5. Варианты арифметики и модификаторов

### N1 — terminal policy

| Вариант | Достоинство | Недостаток/последствие |
|---|---|---|
| AST → один rounding → clamp → проверка типа | Локальная и обозримая граница результата | Bounds могут конфликтовать с integer; нужны compile checks |
| AST → clamp → rounding → проверка bounds | Сначала соблюдается допустимый диапазон raw результата | Rounding может вывести из границ; нужен отказ, не второй незаметный clamp |
| Bounds означают validation, а не clamp | Ошибочная формула не маскируется ограничением | Действие может быть отклонено вместо получения ограниченного результата |
| Округление на промежуточных боевых стадиях | Соответствует правилам, если они явно стадийные | Меняет multi-hit/малые значения; надо перечислить каждую границу |

Предложение архитектуры — первый вариант с одним terminal rounding; это ещё не решение. Нужно отдельно принять, что rounding без precision означает целое, включая отрицательные halfway cases. Промежуточные стадии защиты не округляются по догадке. У integer output с none дробный результат — ошибка, не truncation.

### N2/N3 — числа и единицы

Binary64 проще реализовать на PHP, но даёт двоичные погрешности и требует закреплённого backend/runtime; нельзя обещать произвольный cross-platform replay. Decimal с явным scale предсказуемее для десятичных затрат, но требует выбора precision, политики division и доступной реализации. Int-only не покрывает все разрешённые B2 inputs. Предложение — ограниченный binary64 для formula AST и отдельный точный AP/quantity representation, либо единый согласованный decimal backend. Коэффициенты, precision и epsilon в этапе C не назначаются.

Нужен execution-policy manifest: разрешённые output/input units, bindings actor/target/equipment/status, диапазоны и происхождение. Static profile parameters и dynamic bindings не пересекаются. Решение об одобрении формулы фиксируется по key+version+fingerprint; переиспользование version после изменения fingerprint требует нового одобрения. Достаточность версии без fingerprint не принимается.

### M1 — проценты и порядок

| Вариант | Алгоритм | Балансовое следствие |
|---|---|---|
| Аддитивные проценты от фиксированного B | delta = B * sum(p)/100 | Бонусы не усиливают друг друга; надо выбрать B: исходная база или post-flat |
| Последовательные относительные проценты | v = v * (1+p/100) для каждого | Компаундирование усиливает сочетания; порядок с set/flat существенен |
| Разделённые buckets | Аддитивно внутри явно названной группы, multiply между группами | Более гибко, но нужна дополнительная явная группировка правил, её сейчас нельзя выдумать |

Предложенный в основном документе порядок внутри priority — set → flat → additive percent → multiply; альтернативно весь список исполняется строго последовательно. Нужно выбрать направление priority, смысл равных приоритетов, базис процентов, фазу condition read и поведение нескольких set. Рекомендация для конфликтующих set — отклонение вместо случайного победителя. Для clamp допустимо пересечение ограничений либо строгое последовательное применение; при несовместимых границах нужен отказ. Optional modifier bounds не получают автоматически смысл «ограничить итоговый stat».

## 6. Варианты боевых формул

Буквы ниже обозначают параметры будущего утверждённого определения. Ни коэффициенты, ни пределы здесь не назначены. Формулы, которых не хватает в KB, должны появиться как approved formula_def/profile и policies в отдельной задаче, без переноса legacy CS коэффициентов.

| Механика | Варианты | Преимущества и риски |
|---|---|---|
| H1 accuracy/evasion | Аддитивная разность с базовым шансом и clamp; отношение accuracy к сумме; explicit auto-hit | Разность проще калибровать, но насыщается; отношение зависит от масштаба и требует обработки нулей; auto-hit убирает уклонение и требует явной области |
| Источник evasion | Отдельный ACS stat/source binding; явная KB формула производной характеристики | Отдельный stat прозрачен, но требует данных; производная связывает баланс с исходным stat. Speed сам по себе не утверждён как источник |
| C1 crit_dmg | Полный multiplier; bonus-percent над обычным воздействием | Одинаковое число имеет разный смысл; требуется explicit unit/binding, не угадывание по названию |
| Crit granularity | Один roll на действие; на цель; на hit | Общий roll увеличивает корреляцию и разброс; per-hit сглаживает, но увеличивает RNG/event объём. Для crit heal/shield отдельное разрешение |
| D1-balance исходная мощность | Прямой formula_ref; profile с pinned formula + parameters; явно constant effect | Все варианты могут быть детерминированы. Profile без formula_def не годится; коэффициенты выбирает автор правил |
| DEF | Плоское вычитание; рациональное снижение с параметром масштаба; percentage reduction | Вычитание может обнулять частые слабые hits; рациональная модель плавнее, но зависит от масштаба; процентная требует caps и модели stacking |
| D2-balance resistance | Процент входящего воздействия; плоское поглощение; отдельная формула по rating | Разный эффект на multi-hit и сильные удары. Unit/scope обязательны; отрицательное число не означает vulnerability без правила |
| Иммунитет | Полная блокировка scope; исключение конкретных эффектов; проверяемая условием защита | Нужно определить on_hit/on_damage triggers, расход и статусные компоненты при блокировке |
| True damage | Пропуск только DEF; пропуск выбранных reductions; иной явный маршрут | Разный масштаб урона; нельзя автоматически пропустить shields/immunity |
| Hybrid | Несколько независимо считаемых компонент | Прозрачно, но нужна явная разбивка величины и правило общего crit/hit; усреднение защиты не принимается |
| S1 shield order | Priority затем возраст; ближайшее истечение; выбор владельцем до seal | Возраст проще воспроизводить; expiry бережёт долгие shields; ручной выбор усложняет queue. Решение должно быть фиксировано до исхода |
| Overheal | Отбросить с отдельной записью; преобразовать явной отдельной механикой | Первое проще; второе может менять ценность лечения. Автоматического превращения в shield нет |
| L1 zero HP | Нокаут с разрешённым лечением; смерть/особое восстановление; иной declared life state | Меняет доступность ходов, статусов, revive и max HP=0. Утверждённый no-heal max HP invariant действует в любом варианте |

Chance limits, единицы crit_rate, пороги `<`/`<=`, диапазон RNG, многократное снижение и их порядок также требуют фиксации. Формулы probability не ограничиваются произвольным clamp ACS: пределы должны быть утверждены. Для урона и щита должны быть определены правила отрицательного результата и максимально допустимые значения; не трактовать знак как смену типа воздействия.

## 7. Время, затраты, AP и порядок событий

| Решение | Варианты/вопросы | Последствия |
|---|---|---|
| T1 last tick | Сначала tick затем decrement/expire; сначала expiry gate затем tick | Разное число periodic срабатываний на границе; требуется явный пример для duration=1 |
| Repeat/stack | Refresh duration; add stack; replace; independent instances | Нужны правила источников, caps/overflow и порядка on_apply. Токен repeat_rule ещё не алгоритм |
| Status resistance | Отдельный chance check; scaling duration/potency; immunity-only | Влияет на RNG channels и расход; не выводится из damage resistance |
| Cooldown/recharge | Отсчёт со следующего собственного хода; explicit event anchor; round-based | Нельзя приравнять конец текущего хода и начало следующего; заряды отдельны от cooldown |
| Sustain shortage | Снять эффект; приостановить; отклонить фазовый переход с master resolution | Требуются затраты/остатки/момент снятия, иначе ход может зависнуть |
| T2 priority/ties | Stable source order; explicit initiative; отказ при неоднозначном конфликте | Очерёдность может менять конечный урон/смерть; технический SQL order недопустим |
| Condition context | Phase-entry snapshot; актуальное состояние на dispatch | Первое исключает самопереключение; второе допускает реакцию на предшествующие эффекты. Нужна точка чтения |
| Scaling step | Левая либо правая ступень, обработка exact boundary | B3 хранит step, но выбор стороны не задан |
| R1 miss/immune | Полная use-cost; отдельная reduced/refund policy | Меняет риск применения; AP, resource и charge могут иметь разные правила |
| Cost/gain order | Reserve до effects; расход после effects без использования gains для оплаты | Предотвращает самофинансирование; иная механика должна быть явной |
| A1 fractional AP | Запретить в ACS; разрешить с утверждённой точной шкалой | B3 number не утверждает дробный геймплей. При запрете fractional action_cost — diagnostic, не rounding |
| Zero-cost | Usage limit/одноразовая возможность; запрет отдельных zero-cost операций | Иначе append-only очередь даёт неограниченные попытки/нагрузку |
| E1 weapon swap | Единая цена действия; зависимость от слота/типа | Правило «за действие» принято, точную AP цену/парные руки нужно уточнить |
| G1 summons | Право действовать в текущем ходе либо со следующего; source/control-group budget | Меняет эффективность призыва; новый instance не должен создавать новый общий AP |
| Master multi-post | Один claim на monster за раунд; explicit subturn budget protocol | По умолчанию проект запрещает обход entity claim; дробить оставшийся AP между постами без правила нельзя |

Рекомендуемая техническая защита — finite queue/caps и rollback при превышении; это не балансный способ молча игнорировать последние triggers. Точное ограничение боевой механики задаётся typed limits, технические лимиты лишь защищают сервер.

## 8. Очередь, публикация и спорные ситуации

**Q1 — нельзя получить reroll.** Инженерный вариант: sealed prefix не редактируется и не удаляется на сервере; новая очередь для того же права хода запрещена, разрешён только append. Отказ от публикации не даёт новый набор rolls. Мастерский void должен сохранять прежнюю историю и не открывать скрытую повторную попытку. Если требуется разрешать замену цели/способности после seal, нужен отдельный согласованный механизм переноса прежней случайной возможности; в текущий проект он не включён.

При смене state цели возможны:

- Strict conflict: новая проверка/preview с прежними действиями и rolls, затем повторная публикация. Игрок видит актуальный прогноз, но при частых изменениях commit может отклоняться повторно.
- Automatic rebase: на commit вычислить по актуальному состоянию с теми же rolls. Проще опубликовать, но исход может отличаться от preview без подтверждения.
- Для умершей/пропавшей цели: отказ всей очереди и master resolution либо заранее утверждённый invalid-action/no-op с явной стоимостью. Автоматический retarget запрещён. Выбор no-op — игровое решение, не техническая компенсация.

Предложение архитектуры — strict conflict. Резервация AP opportunity и сохранение ledger не являются фактическим списанием AP до публикации. Правила TTL/завершения отказавшегося хода нужны, чтобы не блокировать раунд бессрочно и не выдавать reroll через истечение.

**P1 — публикация.** Требуется проверить возможность общей транзакции MyBB INSERT + ACS + Inventory на развёрнутом ядре. Если её нет, только проверенный pending-post протокол с recovery; нельзя сообщать успешную боевую публикацию с неприменённым ACS результатом. Отдельно решить, как долго модерируемый пост удерживает ход, допускается ли approval после round end и кто разрешает конфликт. Отклонение модерацией не обнуляет ledger. Удаление уже опубликованного текста не возвращает ресурсы автоматически.

**E1/I1 — provenance.** Если CS даёт только totals с экипировкой, свободная combat переэкипировка блокируется до источникового ledger. Нельзя выбрать балансный «приблизительный вычет». Все Inventory мутации, включая Shop/admin/craft, должны уважать bindings/reservations; защиты только в ACS недостаточно.

## 9. Что согласовать перед D3

Обязательные решения для включения реального evaluator:

1. **N1:** смысл rounding, precision и min/max; порядок terminal rounding/bounds; integer output и отрицательные halfway cases.
2. **N2:** numeric backend/диапазоны, loss/overflow policy и границы воспроизводимости. Для decimal дополнительно precision/scale/division; для binary64 — допустимость погрешностей и представимость int.
3. **N3/V1:** реестр unit/input bindings и процедура утверждения key+version+fingerprint; как engine сохраняет совместимость со старыми snapshots. Нельзя считать любой валидный AST одобренной боевой формулой.

До утверждения M1 D3 может исполнять только согласованные standalone formula_def, но не обещать готовность stat/modifier pipeline. H1/C1/D1-balance/D2-balance/S1/L1/T1/T2/R1/A1 нужны перед соответствующими D4–D7; их следует вынести владельцу правил уже сейчас, но не подбирать коэффициенты ради старта D3. Q1/P1/E1/I1 блокируют безопасное включение D8–D11. Формулы, отсутствующие в KB, требуют отдельного authoring этапа с одобрением и точными pinned версиями.

Форма принятия решения: ID → выбранный вариант и точные единицы/порядок → автор утверждения → policy version → связанные KB key/version/fingerprint → разрешённые capabilities/этап D. До этой записи все варианты в документах этапа C остаются предложениями.
