# ACS-REG-UX-01 — Источники и готовность к регистрации

## Лист thread-52

Мастер ACS читает `af_cs_sheets` по UID текущего пользователя и регистрирует по ID строки листа. Публичный маршрут CharacterSheets принимает slug. Для подготовки снимка используется TID выбранной строки, затем явный `af_charactersheets_accept.kb_entry_id` этой темы. ACS также сверяет TID источника и UID владельца в метаданных KB. Доступность страницы листа сама по себе не подтверждает наличие этой связи и право на регистрацию.

В схеме CharacterSheets предусмотрен уникальный UID. Если `ensure_sheet()` не находит лист по TID и slug, он может переиспользовать строку по UID и изменить её привязку. Это возможное объяснение расхождения тем 51 и 52, которое требует проверки состояния БД. По исходникам нельзя установить, существует ли сейчас строка `thread-52`, каковы её ID, TID и UID и какой ключ KB с ней связан. Лист #32 темы #51 не использовался как заместитель.

Для администратора с доступом к БД приведена проверка только на чтение. Подставьте фактический префикс MyBB вместо `mybb_` и сопоставьте результат с UID аккаунта, вошедшего в мастер.

```sql
SELECT s.id, s.slug, s.tid, s.uid, a.uid AS accepted_uid,
       a.sheet_slug, a.kb_entry_id, k.type, k.`key`, k.active
FROM mybb_af_cs_sheets AS s
LEFT JOIN mybb_af_charactersheets_accept AS a ON a.tid = s.tid
LEFT JOIN mybb_af_kb_entries AS k ON k.id = a.kb_entry_id
WHERE s.slug = 'thread-52' OR s.tid = 52 OR s.id = 32;
```

Если строки для темы 52 нет, отдельно проверьте принятую анкету с `tid = 52` в `af_charactersheets_accept` и её `sheet_slug` и `kb_entry_id`. Если связь существует, проверьте `character_meta.source_tid` и `character_meta.availability.owner_uid` в правилах связанной записи.

## Выбор, проверка и подтверждение

Мастер показывает имя из связанной записи KB, с резервом на заголовок темы, а также ссылки на доступный лист и тему. ID листа указан второстепенным текстом. Точный поиск по slug ищет только среди листов текущего владельца. При расхождении TID и slug вида `thread-N` запись блокируется. Если такой slug отсутствует среди собственных листов, мастер сообщает об отсутствии и, когда применимо, о собственной привязке к другой теме. Результат поиска не раскрывает существование или данные листов других пользователей.

Проверка читает выбранный источник без регистрации. При выборе доступны состояния «Требуется проверка», «Готов к регистрации», «Требует исправлений» и «Недоступен по правам». Исправление направляется в анкету или связанную запись KB. Ссылка на редактор KB доступна только при действующем разрешении редактирования.

Подтверждение появляется после успешной серверной проверки и привязано к проверенному источнику и начальному HP. При записи сервер снова проверяет CSRF, разрешения, версию сессии и актуальные определения и экипировку, а затем сверяет отпечаток подготовленного снимка. Если источник изменился, мастер предложит новую проверку. Существующие клиенты API без отпечатка по-прежнему проходят полную серверную проверку записи.

## Accuracy и стихийные RES

- CharacterSheets показывает Точность в ARPG-листе. Подготовка снимка требует подтверждённый источник `character_stats.character_accuracy` либо применимый канонический `accuracy_base`. Для анкеты значение переносит существующий bridge ATF → KB. Проверьте поле Точность, штатную синхронизацию и наличие ключа в исходной записи KB. Значение в интерфейсе проверяйте вместе с исходными правилами.
- Снимок читает стихийные сопротивления из `resistances` в правилах связанного персонажа KB. Для каждого из 17 ключей реестра нужна однозначная запись с `scope: elemental`, `unit: RES` и неотрицательным числовым значением. Ноль допустим как явно заданное значение. В проверенном контракте нет общего источника начальных нулей для персонажей.
- Синхронизация оригинальных персонажей заново формирует правила из анкеты и не переносит `resistances`. При нынешнем контракте добавляйте явные RES через редактор KB после синхронизации оригинального персонажа и перепроверяйте их после повторной синхронизации. Каноническая ветка редактирует существующие правила. Конкретные значения и причины отсутствия Accuracy и RES у листа темы 52 в БД остаются неподтверждёнными.
- Мастер группирует диагностику по коду и объекту. Все отсутствующие RES представлены одним сообщением с отдельными путями. Повторные диагностики Точности объединены в одно сообщение со ссылкой на источник исправления. Остальные коды и пути видны отдельно. Полный список кодов, путей и уровней серьёзности возвращается при проверке и доступен в мастере пользователям с правом аудита.
