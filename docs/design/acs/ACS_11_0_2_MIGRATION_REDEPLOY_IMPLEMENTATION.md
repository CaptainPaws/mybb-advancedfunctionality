# ACS-11.0.2 — Безопасное повторное развёртывание ACS

## Причина блокировки

До hotfix MigrationManager сравнивал SHA-256 исходных байтов PHP-файла с `schema_migrations.checksum` до проверки структуры установленных объектов. Даже смена переводов строк могла завершить активацию ошибкой `ACS_MIGRATION_JOURNAL_MISMATCH` при полном ledger 001–029. Та же проверка была продублирована в Repository и могла блокировать игровые записи. Конкретная причина различия байтов на warprift.ru требует подтверждения диагностикой на установленной копии. База и исходный развёрнутый комплект в рамках PR не исследовались.

## Проверки и подтверждение

- История проверяется по фиксированному реестру. Записи должны образовывать непрерывную последовательность. Для завершённых миграций требуются точное число шагов и отсутствие записи об ошибке. Поздняя запись после незавершённой миграции блокирует обновление.
- Структура сверяется с DDL реестра через метаданные БД. Проверяются таблицы, порядок и свойства колонок, индексы с порядком ключей, уникальностью и видимостью, ограничения, InnoDB, параметры кодировки и формат строк. В ACP выводятся последняя записанная завершённая версия, требуемая версия, результат проверки и место отказа.
- Контрольные суммы сравниваются отдельно. Подтверждение доступно только для полного проверенного ledger и доказанной смены LF ↔ CRLF. SHA-256 обеих сторон должен совпасть с одним из двух байтовых представлений того же файла из зафиксированного набора 001–029. Эталон фиксирует порядок и LF-нормализованные исходники всех 29 DDL-only миграций.
- Перед подтверждением проверяются неизвестные объекты в пространстве имён ACS и локальные признаки проблем с обязательствами. Сюда входят незавершённые публикации, записи восстановления, ожидающие внешние операции Inventory и Balance, контрольные суммы сохранённых запросов и контрактов, а также JSON и состояния custody. Эта проверка не опрашивает внешних владельцев и не заменяет приёмку игровых данных или проверку внешних квитанций.
- Команда подтверждения доступна в ACP через POST с MyBB CSRF и действующими правами `admin.schema.manage` и `admin.lifecycle`. Сервер заново проверяет файлы, журнал, структуру и обязательства под существующей блокировкой обслуживания ACS. В транзакции сохраняется одна диагностическая запись `migration_reconciliation` с идентификатором администратора, временем и парами SHA-256. Ключ записи зависит от проверенного набора расхождений. Повтор того же подтверждения не создаёт второй записи.
- Активация и Repository используют общее решение по журналу и контрольным суммам. Подтверждённые расхождения остаются видимыми в ACP. Журнал миграций сохраняет оригинальные SHA-256 и результаты выполнения.
- Полностью установленная схема обходит DDL runner. При появлении новой миграции штатный MigrationManager обрабатывает только ожидающее продолжение реестра после проверенной истории. Ранее выданное подтверждение сохраняет силу для тех же пар SHA-256. Незавершённая миграция не допускает активацию или новое подтверждение. Явное штатное обновление по-прежнему может продолжить известную непротиворечивую миграцию с проверенными файлами и шагами.

## Действия администратора

1. Загрузить полный проверенный каталог ACS и открыть **AdvancedFunctionality → AdvancedCombatSystem → Основные**. Сверить установленную и требуемую версии и состояние структуры.
2. При `READY` выполнить штатную активацию при необходимости. При `FILE_CHECKSUM_MISMATCH / ACS_MIGRATION_CHECKSUM_CONFIRMATION_REQUIRED` нажать **Подтвердить повторное развёртывание ACS** и повторить активацию.
3. При блокировке без кнопки выполнить рекомендацию ACP. Для недостающих файлов загрузить полный комплект. Для недоказанного расхождения восстановить артефакт исходного развёртывания. При `SCHEMA_DRIFT`, `UNKNOWN_MIGRATION`, повреждённом журнале или проблеме с обязательствами передать код ошибки и указанную версию или таблицу владельцу проекта.
4. Вручную проверить, что под новой копией доступны существующие сессии. Повторить отправку того же подтверждения и убедиться, что запись одна. Сверить сохранность ledger и игровых данных, а также отсутствие включения production publication.

Изменения комментариев, BOM, смешанные переводы строк, любые другие изменения PHP/DDL и неизвестные контрольные суммы требуют исходного комплекта либо отдельного рассмотрения владельцем. Reconciliation не восстанавливает неизвестные исторические байты. При прерванной передаче следует завершить загрузку файлов перед подтверждением.

## Проверки и ограничения

- Выполнена статическая сверка путей ACP POST, активации, install/upgrade и Repository. Подтверждение использует только диагностическую запись. GET и активация не меняют журнал. Новые миграции, изменения зарегистрированного DDL, прав `RESERVED_DENY` или `docs/ROADMAP.md` отсутствуют. Production publication остаётся отключённой.
- `git diff --check` прошёл. PHP CLI в рабочем окружении отсутствует.
- Автоматические, SQL, регрессионные и интеграционные тесты не создавались и не запускались. Фактические SHA-256, структура и обязательства на warprift.ru остаются предметом ручной приёмки владельцем.
