# ACS-REG-05 — Проверка источника и предзаполнение регистрации

## Причина отказа

Производственный журнал для обращения `5c4e6773df1f764902348accd2334150` недоступен. Точный класс, сообщение и место исключения именно в запросе для листа #34 установить по публичному коду обращения нельзя. Установленные версии записей и отпечатки трёх способностей в `oc-52` также требуют сверки на форуме.

В коде найден конкретный отказ на пути `EntityService::prepare()` → `InventoryRead::read()` → `OwnerProtocol::assertStorage()`. Сверка `information_schema.COLUMNS.COLUMN_TYPE` отклоняла, например, `int(10) unsigned` при ожидаемом `int unsigned`. Аналогичная ошибка возникала для `int(11)` и `bigint(20) unsigned`. Это приводило к `RuntimeException('INV_SCHEMA_NOT_READY')` на этапе `inventory_read` и при проверке, и при регистрации. Отказ MariaDB из-за точного сравнения типов ранее зафиксирован в [отчёте ACS 7.1.1](ACS_7_1_1_IMPLEMENTATION.md). Исправление учитывает необязательную ширину отображения целочисленного типа. Проверки знака, типа, индексов, движка таблиц и collation сохранены. Совпадение этой причины с указанным обращением остаётся неподтверждённым.

Дополнительно некорректный JSON настроек листа мог выбрасывать `JsonException` при чтении `build_json`. Теперь нечитаемые настройки возвращают `build_invalid` без изменения листа. При повторном чтении закреплённых способностей проверка пропускает исходное непредвиденное исключение к обработчику ACS. Ожидаемые ошибки определения KB и несовпадение отпечатка имеют отдельные результаты.

## Поток регистрации

- Карточка выбранного персонажа показывает имя и портрет из доступного профиля KB, имя владельца из MyBB, ID листа и ID темы. Максимальное HP берётся из того же боевого расчёта CharacterSheets, который читает проверка ACS. Текущее HP используется только при наличии подтверждённого значения источника. В текущем контракте CharacterSheets поле текущего HP пустое, поэтому для новой регистрации предлагается проверенный максимум. GM может уменьшить его перед проверкой.
- Имя экземпляра и причина редактируются в форме подтверждения. Предложенная причина — «Добавление персонажа в столкновение». Регистрация требует отдельного POST с причиной, допустимым HP, версией сессии, ключом операции и отпечатком подготовки. Затем используется штатное добавление на сторону. Исходный лист и существующие боевые снимки сохраняются.
- Проверка использует текущего актора MyBB и тот же серверный грант GM для сессии, листа, владельца и темы. Грант также проверяется при чтении инвентаря. Карточка получает только разрешённые метаданные и HP. Модальное окно заменяет карточку и сохраняет выбранную вкладку и столкновение.
- Для ссылок на способности CharacterSheets использует определение KB и сверяет закреплённую версию и отпечаток. Изменившаяся версия требует повторного выбора способности и синхронизации. Для эффекта «Каменная кожа» единица `round` поддерживается. Фактические записи `acs_test_stone_skin`, `acs_test_bandage`, `acs_test_defender_stance` на форуме предстоит сверить отдельно.
- Технический отказ записывает в штатную диагностику ACP код обращения, этап и операцию `entity_validate` или `entity_prefill`. Серверный журнал по тому же коду содержит класс исключения, допустимый машинный код и место сбоя. SQL, стек и данные персонажа в ответ или журнал диагностики не попадают. Проверка не создаёт боевых записей и не регистрирует существо.

## Проверка

Выполнены точечные `php -l`, `node --check` и `git diff --check`. Автоматические тесты не создавались и не запускались.

Ручная приёмка на форуме остаётся открытой. Выбрать лист #34, сверить имя, портрет, владельца и HP, затем повторить проверку без регистрации. При техническом отказе сопоставить новый ID с ACP и серверным журналом. Отдельно проверить отказ по правам, устаревший отпечаток способности и регистрацию разрешённого второго листа. После явного подтверждения добавить персонажа на сторону и обновить страницу. Сверить, что исходный лист сохранился и повторная проверка не создала дубликат.
