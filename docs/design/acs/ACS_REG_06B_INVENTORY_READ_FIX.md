# ACS-REG-06B — Исправление чтения Inventory при проверке источника

## Подтверждённый дефект

`AF_ADVINV_InventoryRead::__construct()` требует от авторитетного соединения кодировку `utf8mb4`. До исправления `EntityService::prepare()` в режиме `entity_validate` входил в конструктор после выхода из временной области настроек предыдущего запроса ACS. Эта область восстанавливает исходную кодировку MyBB. Если MyBB настроен на другую кодировку, конструктор выбрасывает `RuntimeException('INV_UTF8MB4_REQUIRED')` до авторизации Inventory и чтения таблиц. Команда регистрации входит в ту же подготовку из транзакции ACS, где действующая область уже устанавливает `utf8mb4`. Это подтверждённое расхождение жизненного цикла соединения между проверкой и записью.

Записи боевого ACP, включая `85cf62dd2b93a0cbb7342b9738d49bd5`, подтверждают фазу `inventory_read`. Старый формат сохранил категорию без машинного кода исключения. Журнал сервера и конфигурация соединения форума в рабочем окружении недоступны, поэтому точное исключение этого обращения и установленная схема Inventory остаются неподтверждёнными.

## Исправление и границы

- Ветка персонажа проверяет идентичность writer-соединения и использует на нём существующую область `AF_ACS_TransactionManager::databaseSettings()` при создании и чтении `AF_ADVINV_InventoryRead`. Область восстанавливает настройки в `finally`. В транзакции регистрации повторная область переиспользуется. Проверка по-прежнему не входит в `fence()`; ограждение версии выполняется только при записи.
- Конструктор продолжает требовать `mysqli`, `utf8mb4` и совместимое соединение чтения и записи. Авторизованный актор берётся из MyBB. Для чужого листа чтение проверяет серверный грант сессии, получает UID владельца из гранта и использует его во всех выборках Inventory. Остались проверки состава страниц, версии владельца, экипированных и вспомогательных слотов и активных резервов, а также возврат полного `AF_ADVINV_InventoryReadResult` для сервера.
- `af_inv_get_items()` объявлен в основном bootstrap AdvancedInventory. Обычная маршрутизация ACS и страница Inventory получают его через загрузку включённых аддонов на `global_start`. Контекстные маршруты манифеста относятся к доставке frontend-ресурсов. По коду не выявлено отдельного штатного пути ACS, который при включённом аддоне пропускал бы этот bootstrap.
- `OwnerProtocol::assertStorage()` по-прежнему требует действительные таблицы, движки, колонки и индексы. При сбое он сообщает только идентификатор проверяемого компонента, например `table.owner_state`. Если новый запрос укажет на отсутствующую owner-таблицу, администратор может сверить установку с явным DDL-планом `AF_ADVINV_OwnerSchema::statements()` и применить предусмотренное обновление в обслуживании. Структура БД при чтении не меняется.
- Существующий `recordDiagnostic()` сохраняет безопасный код и, при наличии, компонент в `details_json`. ACP проецирует только эти поля при просмотре списка и поиске по коду обращения. Старые записи показывают сохранённую категорию. При ошибке драйвера чтения используется `INV_READ_FAILED`. SQL, стек, параметры запроса и данные Inventory в ACP и ответ проверки не выводятся.

## NPC и монстры

Оба вида читают определение `arpg_bestiary` в фазе `source_read`. Затем выполняются проверки характеристик, начального HP, закреплённых способностей и сериализации. Ветка `inventory_read` достигается только при `kind=character`. Конкретная фаза фактического отказа NPC или монстра на форуме не установлена. Для её проверки нужен отдельный запрос под каждым видом с сопоставлением кода обращения в ACP.

## Проверка

Выполнены точечные `php -l` и `git diff --check`. Автоматические тесты не создавались и не запускались.

На форуме остаётся вручную проверить лист #34 владельца UID 5 в сессии #2 и при готовности отдельно подтвердить регистрацию и добавить персонажа в состав. Сверить экипировку снимка с Inventory владельца и состояние Inventory до и после. Если проверка снова вернёт технический отказ, ACP должен показать код и, для дефекта схемы, компонент. Ручная проверка регистрации NPC и монстра выполняется отдельно.
