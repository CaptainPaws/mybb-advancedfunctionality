# ACS-REG-07 — Транзакция регистрации персонажа

## Что установлено по коду

В `InventoryRead::fence()` существовал повторный SQL-запрос `SET TRANSACTION ISOLATION LEVEL READ COMMITTED` после `begin_transaction()` в ACS. MySQL и MariaDB отклоняют смену характеристик уже открытой транзакции. Старый код использовал этот отказ как проверку состояния и продолжал блокировку Inventory только при исключении `mysqli_sql_exception` с кодом 1568. При любом другом отказе подготовки или выполнения запроса регистрация останавливалась до чтения Inventory. `@@autocommit=1` совместим с явно начатой транзакцией и сам по себе не доказывает её наличие. Проверка источника этот путь пропускает.

Это конкретный дефект контракта вызова. Если сервер возвращал 1568, старая ветка продолжала работу. По имеющемуся `error_id=87a73da524cbc16e02de89875e65afbb` производственную причину установить нельзя. Прежняя запись содержит общую категорию и не различает блокировку Inventory, сохранение сущности и завершение операции. Серверный журнал в рабочем окружении недоступен.

## Исправление

- При регистрации персонажа `InventoryRead::fenceForAcsRegistration()` проверяет, что именно его `mysqli` отмечен как активный в существующем реестре ACS `TransactionManager`. Реестр пополняется после успешного `begin_transaction()` и очищается в `finally`. Блокировка больше не зависит от намеренно отклоняемого SQL в этой ветке.
- На том же соединении Inventory повторно авторизует GM по гранту владельца листа. Под транзакцией создаётся строка версии только при её отсутствии. Затем берётся блокировка этой строки `FOR UPDATE` и читаются версия, предметы, экипировка, вспомогательные слоты и резервы с действующими проверками. Inventory не меняет количества или привязки и не завершает транзакцию.
- Действующий порядок сохраняется. ACS блокирует сессию и проверяет ключ операции и CAS, затем блокирует состояние Inventory. После сверки отпечатка ACS сохраняет снимок, сущность, проекцию экипировки, событие и результат операции, затем выполняет commit. Исключения до commit приводят к общему rollback. Зафиксированная операция возвращает прежний результат по тому же ключу до повторной подготовки источника. Проверка единственной регистрации листа в сессии сохранена.
- Ошибки регистрации персонажа в GM записываются как `entity_register` в существующий журнал ACS. Сохраняются код обращения, этап, безопасный машинный код и, где применимо, `inventory.fence`, `inventory.read`, `entity.persist` или идентификатор компонента схемы. Валидация и известные конфликты отображаются отдельно. Неопределённый исход сохраняет сценарий восстановления с прежним ключом. NPC и монстры продолжают использовать прежний маршрут.
