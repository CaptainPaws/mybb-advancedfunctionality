# ACS-2.3.3 — управление раундами

Исходная main: `d789c8815c5a4497c00b4ee25f937a04fee1413b`.
Версия ACS: 0.9.0. Схема остаётся `005_clock_resources`; новых миграций нет.
Design Baseline и четыре нормативных документа не изменены.

## Серверные операции

`EncounterService::rounds()` возвращает `RoundManagementService`. Read-only
`overview()` показывает текущую политику и остаток времени. `command()` принимает
pause, resume, deadline_set, extend_deadline, gm_skip, gm_forfeit,
deadline_process и round_next. AF XMLHttp использует префикс `round_manage_`;
существующая панель ATF отправляет те же команды через POST.

Каждая команда проверяет штатный доступ к теме/сессии, роль owner/GM либо
существующие административные полномочия ACP, CSRF, подтверждение, причину,
версии сессии/столкновения/хода и operation_key. Нет повышения GM до владельца
чужого персонажа. Используются существующие транзакции, блокировка команд,
CAS, append-only события и идемпотентные маркеры Clock. Повтор того же ключа
с другим содержимым отклоняется. Повтор закрытия хода или перехода раунда
с другим ключом возвращает уже зафиксированный результат.

Pause сохраняет AP и состояния ходов, замораживает остатки дедлайнов. Resume
восстанавливает остатки от времени команды без догоняющих тиков и обновления AP.
Политика дедлайна по умолчанию off. Явно доступны notify, timeout_pass и gm_skip;
длительность задаётся для конкретного столкновения. Изменение политики создаёт
новый immutable снимок конфигурации. Notify фиксирует наступление срока без
пропуска; timeout_pass закрывает только действительно просроченный pending turn.

GM skip переводит pending в passed. Forfeited допустим только при подтверждённом
выходе всех участников замороженной группы (withdrawn/escaped/captured/surrendered).
Смерть или недееспособность сами по себе не закрывают ход. Поддерживаемые
индивидуальные start/end boundaries выполняются однократно. AP не возвращаются.
Незавершённые обязательства, drafts/sealed tape и неподдерживаемые effects
блокируют операцию; данные не удаляются и не отменяются.

Следующий раунд создаётся после закрытия roster и проверки индивидуальных
границ, pinned snapshot hashes и готовности участников. Используется общий
конструктор roster: новые группы входят в следующий раунд, закрытые ходы
сохраняются. Новый AP и допустимые cooldown boundaries применяются один раз.
Параллельные GM-команды защищены общей блокировкой и CAS.

## Ограничения / BLOCKED

- Безопасный ACS system-authority scheduler отсутствует. Автономная фоновая
  обработка timeout BLOCKED; сейчас доступна явная авторизованная POST-команда GM.
  GET, просмотр панели и обновление страницы не обрабатывают тайм-ауты.
- Доставка уведомлений IC-AAM относится к этапу 11 и BLOCKED. Notify записывает
  событие наступления срока, но не заявляет, что сообщение доставлено.
- Будущие неподдерживаемые эффекты/обязательства блокируют границу вместо
  небезопасного пропуска. Публикация, seal, атаки и Resolver не реализованы.
- Реальная система постоянных питомцев ожидает будущий provider; общая группа
  проверена утверждённым fixture, без создания фиктивной собственности.

## Минимальные проверки

Все затронутые PHP-файлы прошли php -l; git diff --check чистый.
Локально PHP 8.4.24 и изолированная MariaDB 10.11: target PHP 8.5.0 требует
ручной проверки на форуме. Production не использовался.

Точечный acs_round_management_regression прошёл: pause/resume и frozen deadline,
сохранение AP, notify без skip, timeout_pass, повтор notice после смены политики,
duplicate skip, запрет произвольного forfeiture, сохранение sealed draft,
обязательные EntityTurn boundaries, duplicate next round, late-group admission,
AP refresh ровно один раз, отказ игроку, отсутствие мутаций GET и исходных аддонов.
Конкуренция проверена двумя mysqli-соединениями (занятая advisory lock), а также
устаревшей версией команды другого GM. Сценарий использует существующие точечные
fixtures roster/entities/encounters; полный suite не запускался.

Дополнительно прошли точечные acs_clock_resources_regression (AP/cooldown/rest)
и acs_sessions_regression (включая deactivate/activate с сохранением данных).
Массовых E2E, стресс-тестов и браузерных проверок не было.

## Ручная приёмка

1. Открыть подготовленное столкновение как GM и запустить первый раунд.
2. Установить дедлайн; pause должен сохранить AP/ходы и заморозить остаток.
3. После resume остаток отсчитывается заново без дополнительных тиков.
4. Выполнить gm_skip с причиной; повтор POST не создаёт второе событие.
5. Для notify обработать наступивший срок: ход остаётся pending. Для timeout_pass
   явная команда обработки закрывает просроченный ход ровно один раз.
6. После допустимого закрытия всех ходов перейти к следующему раунду. Проверить
   roster, независимые группы монстров, AP и cooldown; повторить запрос.
7. Проверить отказ обычному пользователю и сохранность данных после перезагрузок.
8. Проверить обычную тему, CharacterSheets и Inventory: просмотра недостаточно
   для изменения состояния. Проверить реактивацию ACS.

При ошибке сохранить журнал и состояние, устранить причину BLOCKED и повторить
исходную команду с тем же operation_key. Не сбрасывать ledger/версии SQL вручную.
Для безопасного отката отключить ACS с сохранением таблиц. Версия 0.8 не умеет
управлять новыми paused/multi-round состояниями: не включать её поверх активной
сессии без отдельной проверки совместимости и резервной копии. Этап 3 не начат.
