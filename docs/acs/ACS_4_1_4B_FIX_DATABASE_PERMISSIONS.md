# ACS-4.1.4B-FIX — точная диагностика доступа и pre-DDL recovery

> Исторический отчёт. По ACS Stage 4 Revision 2 мигратор полностью удалён из репозитория; приведённые пути и команды больше не действуют. Актуальное состояние: [ACS-4.0-CLEANUP](ACS_4_0_CLEANUP.md).

Исходная main: `a4334ee6ba6824aeb74cf9d303bf5ebdf9b78a97` (PR #1012 принят). Production ALTER/изменения прав не выполнялись. IC-MYBB-1 остаётся BLOCKED. Игровая механика и правила преобразования не меняются.

## Первопричина

В `AcpExecution::command()` SQL ошибки 1044/1045/1142/1227 независимо от запроса превращались в `database_permissions`, а любой отказ — в `recovery_required`. Место ошибки не записывалось. Поэтому старый отчёт `migration:null`, десять MyISAM и `database_permissions` **не позволяет задним числом доказать конкретный отказавший запрос установленного warprift.ru**. Ни engines, ни отсутствие UI progress сами по себе не доказывают отсутствие незавершённого DDL.

В изолированном **MySQL 8.0.46** воспроизведён соответствующий сценарий: учётная запись с `ALL ON forum_schema.*`, но без глобального `REPLICATION CLIENT`, проходит schema/TRIGGER проверки, затем получает **1227 на `SHOW REPLICA STATUS`**, до LOCK TABLES/создания Engine state/ALTER. Это конкретная воспроизведённая причина, но не объявляется подтверждённым фактом production без новой диагностики. Отдельно воспроизведён **1044 на `LOCK TABLES … WRITE`** после отзыва LOCK TABLES при наличии REPLICATION CLIENT.

## Изменения

- Общее ядро сохраняет фиксированный идентификатор отказавшей SQL-операции и errno: replication status, LOCK TABLES, SHOW GRANTS, TRIGGER/FK/table metadata, SHOW CREATE/COLUMNS/INDEX, чтение данных, ALTER, mutex/session/identity. Ошибки прав отделены от иных SQL ошибок. Raw SQL, MySQL error text, аккаунты и credentials не попадают в UI/export.
- В существующую кнопку «Проверить готовность» добавлены независимые **read-only** probes: SHOW REPLICA STATUS, собственные SHOW GRANTS, metadata inventory, SHOW INDEX и SELECT LIMIT 0 для каждой разрешённой таблицы. Отказ одного probe не скрывает остальные. Нет пробного LOCK/ALTER, GRANT или изменения global modes. Отказ чтения общей схемы также не скрывает отчёт отдельных probes.
- В «Технических подробностях» — результат каждого probe, errno, требуемое право и SQL-операция. Конкретный отказ, записанный исполнителем, виден рядом с основной кнопкой. В export — только allowlisted статусы и числовые коды, не исходные SHOW GRANTS/свободный текст.
- `DIRECT_GRANT` означает только обнаруженный прямой grant, не успешность ALTER. `NOT_VERIFIED` не означает доказанный запрет: роли/частичные grants и ограничения visibility могут требовать проверки хостингом. Успешный SELECT из information_schema.TRIGGERS сам по себе не доказывает полноту списка; прежний строгий TRIGGER gate сохранён.
- После владения **обоими** migration mutex и проверки identity/hash существующего Engine journal ядро фиксирует, был ли pending intent. При доказанном pre-DDL отказе job становится `ready` с сохранёнными error/errno/operation/`before_ddl`. После предоставления прав можно продолжить ту же операцию. Никакого удаления журнала, reset baseline или повторения completed таблиц.
- Флаг становится консервативным до записи нового intent. Если intent уже существовал, ALTER мог начаться, состояние повреждено/не читается или mutex не получен — сохраняется recovery gate. Ошибка асинхронного ALTER также не превращается в pre-DDL. `recover` никогда не исполняет ALTER; неизвестный результат сверяется прежним протоколом.
- Старый `recovery_required/database_permissions` не сбрасывается по GET или по одному `migration:null`. «Проверить результат» проверяет mutex и authoritative journal. Если доказано отсутствие intent, даже повторный отказ preflight получает точный код и возвращает `ready`; если доказательства недоступны — блокировка сохраняется. История и operation receipts остаются.

## Минимальные разрешения: только по фактически отказавшему запросу

Изменяет права **только DBA/хостинг**, не ACS. Имена ниже — шаблоны, не сведения об учётной записи warprift.ru.

| Отказ | Требование MySQL 8.0.46 / действие хостинга |
|---|---|
| SHOW REPLICA STATUS, errno 1227 | `GRANT REPLICATION CLIENT ON *.* TO '<forum-user>'@'<forum-host>';` — минимальное отдельное право для этого запроса; SUPER не нужен. Если политика shared hosting запрещает доступ, gate остаётся, нужен управляемый запуск владельцем сервера. |
| LOCK TABLES … WRITE, errno 1044/1142 | `GRANT LOCK TABLES ON <forum_db>.* TO '<forum-user>'@'<forum-host>';` и SELECT на все базовые таблицы этой схемы: barrier блокирует также не конвертируемые таблицы. Это не разрешение ALTER других таблиц. |
| Проверка полноты triggers | Прямой TRIGGER на схему форума; проверяются собственный SHOW GRANTS и information_schema.TRIGGERS. Пустой результат без доказанной visibility не принимается. |
| SHOW INDEX/CREATE/COLUMNS, SELECT данных | Проверить доступ к нужной таблице, включая SELECT и полноту metadata. Мастер не требует SELECT на mysql.* ради собственных SHOW GRANTS. |
| ALTER … ENGINE=InnoDB | ALTER, CREATE, INSERT на преобразуемую таблицу (плюс SELECT для проверки данных). Права можно выдавать на конкретные разрешённые таблицы. При уже записанном intent сначала recovery, не повтор ALTER. |

Не выдавать все глобальные права для устранения неопределённой ошибки. Приложение ничего не расширяет, REPLICATION CLIENT не подменяется SUPER, а блокировка записей/структурные проверки не обходятся.

## Проверки

Только изолированная MySQL 8.0.46 (`--network none`), synthetic `acs414b_test/fixture_`, PHP 8.4.24; установленный PHP 8.5.12/FPM не объявлен протестированным.

- `php -l` изменённых PHP; целевые wizard и CLI regression без полного suite.
- Реальная ограниченная учётная запись: независимые read-only probes продолжаются после 1227; отказ до DDL фиксируется точно и даёт ready; повтор ключа не выполняет работу.
- Legacy recovery_required + нет Engine intent: безопасный переход ready без удаления журнала и потери событий.
- Отдельный реальный LOCK TABLES denial 1044; после предоставления прав продолжение той же операции и один ALTER.
- Pending intent + отказ SHOW REPLICA STATUS: gate остаётся recovery_required. После предоставления права исход подтверждается без повторного ALTER.
- Ранее выполненные таблицы/история сохраняются; десять последовательных конверсий с data digest, FULLTEXT/индексами/AUTO_INCREMENT; schema drift, потерянный completion, повтор/уже InnoDB — целевой regression сохранён.
- Отдельная fixture проверяет, что в probes/export нет raw error, grant rows, аккаунтов, путей и секретов; диагностические запросы только SELECT/SHOW. Production не использовался.

## Для администратора warprift.ru

1. Обновить код PR, открыть прежний мастер и нажать «Проверить готовность». В подробностях посмотреть конкретный запрос/errno; при необходимости передать безопасный export хостингу.
2. При старом recovery_required нажать **«Проверить результат»**, не удалять файлы/cache журнала. Этот вызов не запускает ALTER. Он уточнит ошибку и снимет gate только при доказанном отсутствии незавершённого intent.
3. Если отказ — SHOW REPLICA STATUS/1227, попросить хостинг проверить REPLICATION CLIENT для пользователя форума; если другой запрос — исправить указанное разрешение. Не выдавать лишние права по предположению.
4. После исправления повторно проверить готовность. Продолжать существующую миграцию только в согласованное окно с backup/закрытым форумом. Данный PR не запускал production миграцию.
