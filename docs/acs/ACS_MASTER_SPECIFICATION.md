## 2. Числовое ядро и характеристики

### 2.1. Арифметика — N1, N2

Используется ограниченная PHP binary64: фиксированный порядок операций, проверка конечности, деления на ноль, переполнения и потери допустимой точности. AP, количества предметов и прочность барьеров — целые. Дробные промежуточные величины сохраняются. На конечной границе: установленная политика rounding, затем clamp min_value/max_value. Стандарт для конечного целого — half_up; явно заданную выходную политику formula_def нельзя молча заменить. Один результат не округляется дважды. Некорректные или несовместимые с целым результатом границы — ошибка, не исправляемая clamp.

Граница формулы отличается от границы ресурса: лечение 500 при HP 1900/2000 имеет рассчитанную величину 500, эффективное восстановление 100 и избыточное 400. Для смешанного удара действует уточняющее D1.13 (§3).

### 2.2. Модификаторы — M1

Нормализованные ACS-модификаторы не переопределяют legacy `flat`/`percent` KB и CharacterSheets. Без set базовая последовательность одной стадии:

```text
v_flat = base + sum(add_flat)
v_percent = v_flat * (1 + sum(add_relative_percent)/100)
v_mult = v_percent * product(multiply)
```

Внутри разрешённых фаз меньший priority обрабатывается раньше. Priority не переставляет типы «плоские → проценты → множители». `set` в окончательной редакции принудительно задаёт итог, который обычные бонусы больше не меняют. Выигрывает наибольший priority; одинаковые значение и priority совместимы, разные значения при равном priority — ошибка всей операции без изменения состояния и переброса. `clamp_min`/`clamp_max` проверяют допустимые конечные границы; противоречивые ограничения — ошибка определения.

### 2.3. Характеристики — H1, C1, D1, S1.2

Accuracy и Speed — неотрицательные числовые показатели, не проценты. Accuracy должна быть полноценной характеристикой KB/CharacterSheets, доступной происхождениям, предметам, талантам, способностям и бестиарию. Luck не участвует в обычном попадании, глобально не повышает добычу; специальные эффекты используют её только явно через KB. `status_hit` и `status_resistance` управляют вероятностью негативных статусов, не силой и длительностью уже наложенного эффекта. Существующий SQL/KB ключ `status_resist` требует явного технического сопоставления с термином baseline `status_resistance`, см. IC-KB.

Нельзя выдавать старым персонажам произвольные 100 accuracy или угадывать шкалу отсутствующей характеристики. Подготовка данных — отдельная задача до допуска такого персонажа в бой.

## 3. Попадание, крит, защита и последствия

### 3.1. Обычное попадание — H1

```text
A = effective accuracy; S = effective speed
P_hit = 75, если A=S=0
P_hit = clamp(75 + 30*(A-S)/(A+S), 5, 95), иначе
P_evade = 100 - P_hit
```

Один серверный бросок означает попадание либо автоматическое уклонение; второго броска на уклонение нет. При неотрицательных A/S фактически достижимый диапазон обычной формулы 45–95%; нижний clamp 5% сохраняется как утверждённая страховочная граница. Равные показатели дают 75%. `auto_hit` и специальные исключения задаются KB, не выводятся из Speed=0 или из литературного текста. Результат запечатывается до публикации и доступен для написания отыгрыша с соблюдением секретности.

### 3.2. Крит — C1, C1.2–C1.4

У каждого отдельного удара собственной многократной способности свои hit/crit-проверки. Один crit-бросок относится ко всему удару, а не к каждому компоненту. `crit_rate` ограничен 0–100%; `crit_dmg` — дополнительный неотрицательный процент без глобального потолка:

```text
critical_component = raw_component * (1 + crit_dmg/100)
```

Множитель применяется после исходного расчёта, до DEF/RES, только к компонентам, допускающим крит. Обычные атаки и прямые атакующие способности критуют по умолчанию. DoT, отражение, природный урон, лечение и щиты по умолчанию не критуют; явный контракт KB может разрешить или запретить это для эффекта.

### 3.3. Типы, пробивание и сопротивления — D1–D1.16

`physical` снижается DEF; `elemental` — RES своей стихии; `true` игнорирует DEF, RES и обычные барьеры, идёт в HP. Действующий набор — 17 основных стихий по последующему утверждённому уточнению [D1.4 (ACS-DOC-01)](#d1-4). Канонические ключи приведены ниже; похожий legacy damage_type не определяет стихию автоматически.

```text
penetration_percent = clamp(sum(percent_penetration),0,100)
penetration_flat = sum(nonnegative flat_penetration)
DEF_eff = max(0, DEF*(1-penetration_percent/100)-penetration_flat)
RES_eff[e] = max(0, RES[e]*(1-percent_penetration[e]/100)-flat_penetration[e])
physical = raw_after_crit * 100/(100+DEF_eff)
elemental[e] = raw_after_crit * 100/(100+RES_eff[e])
elemental[e] *= 1 + sum(nonnegative vulnerability[e])/100
```

DEF/RES — числовая неотрицательная защита. Отрицательная RES не моделирует уязвимость. RES и уязвимость могут сосуществовать, RES применяется раньше уязвимости. Уязвимости одной стихии аддитивны, без глобального потолка. Элементальный иммунитет обнуляет соответствующий компонент до бюджета независимо от уязвимости; иммунитет статусов независим. Фиксированное пробивание не имеет глобального потолка. Пробивание не меняет защиту цели для других атакующих; отдельного контрпробивания в ACS 1.0 нет.

Каждая из 17 основных стихий имеет собственный неотрицательный числовой показатель `RES_element`. Формула D1.4 сохраняется: `elemental_damage × 100 / (100 + RES_element)`. Воздух имеет каноническое имя `air`; существующий KB-ключ `wind` требует совместимости на границе данных без разрушительной миграции. Бездна не равна Тьме, Жизнь и Смерть различны, Пространство и Гравитация различны, Астрал и Разум различны.

Дочернее магическое направление имеет стабильный технический ключ и ровно одного родителя: основную стихию либо другое направление в допустимой ациклической иерархии, восходящей к основной стихии. Оно может иметь описание, оформление, иконку и ссылки KB, классифицировать способности, таланты и специализации. Новые направления добавляются через KB без изменения PHP-реестра основных стихий. Количество направлений не имеет искусственного игрового лимита; технические пределы хранения, валидации и производительности сохраняются.

| Родитель | Примеры направлений (не автоматический seed) |
|---|---|
| Жизнь `life` | Кровь `blood`, Регенерация, Биомантия |
| Земля `earth` | Металл `metal`, Кристалл `crystal`, Песок |
| Воздух `air` | Звук `sound`, Вибрация |
| Смерть `death` | Некромантия |

**Дочерние направления не получают отдельный базовый RES. Кровь не входит в число 17 основных стихий.** Магическое направление способности, фактический тип воздействия и применяемая защита — разные данные. Способность направления `blood` может наносить physical-урон, elemental-урон Жизни, накладывать статус или восстанавливать HP — только по явному утверждённому определению KB. Родитель `life` не делает любое воздействие Крови уроном Жизнью. При elemental-уроне применяется только RES явно указанной основной стихии `damage_element`; направление не создаёт дополнительную ступень сопротивления. Иерархия не вводит автоматических бонусов, множителей, контрстихий или elemental reaction matrix.

### 3.4. Единственный целочисленный бюджет удара — D1.10–D1.13

1. Рассчитать компоненты и крит без округления.
2. Применить иммунитеты, эффективные DEF/RES и уязвимости.
3. Сложить компоненты и один раз half_up получить целый бюджет B.
4. Взять floor каждого неотрицательного компонента; оставшиеся `B-sum(floor)` единицы отдать наибольшим дробным остаткам. При равенстве первым идёт меньший сохранённый индекс KB.
5. Обработать целые компоненты в сохранённом порядке KB, расходуя подходящие барьеры.
6. Остаток списать с HP без повторного округления, не опуская HP ниже 0.

Порядок компонентов имеет механическое значение и входит в snapshot/seal. True входит в общий бюджет, но обходит обычные барьеры. Сумма целых компонентов строго равна B. Успешное попадание может дать ноль урона; гарантированного минимума 1 нет. Примеры проверки: `0.4+0.4 → 1+0`; `1.4+1.4+1.2 → 2+1+1`; `2.7+1.8+0.6 → 3+2+0`. Это примеры утверждённого алгоритма, не отдельные балансные параметры.

### 3.5. Барьеры — D1.7–D1.10, A1.22–A1.24

Каждый экземпляр имеет прочность, максимум, длительность, источник, область и фильтр `absorbs`. Индивидуальный `per_target` имеет свой запас; `shared_pool` — один запас на всех защищаемых. Одна очередь: явный KB `barrier_priority`, затем FIFO времени создания, затем стабильный ID. Без переопределения применяется FIFO. Каждый компонент проверяет фильтр. Shared pool расходуется последовательно по запечатанному порядку целей; разрушение немедленно убирает защиту у всех.

Повтор того же барьера от того же источника в той же области по умолчанию заменяет экземпляр и перемещает новый в конец FIFO. `restore` восстанавливает существующий до максимума, не меняя очередь и срок, не оживляет разрушенный. Stack допускается явно через KB с лимитом и независимыми экземплярами.

### 3.6. HP, восстановление и отражение — S1.12, A1.11–A1.12, A1.25–A1.27

При 0 HP немедленно `incapacitated`, не автоматическая смерть. Лечение выше 0 возвращает `active`, если нет иных ограничений. `dead` подтверждается отдельно, обычное лечение не воскрешает. Стоимость в HP обходит защиту, не является уроном и не запускает on_hit/on_damage; обычно оставляет минимум 1 HP. Явная KB-жертва может довести до 0, но не превысить запас; действие завершается, дальнейшие обычные действия запрещены.

Вампиризм использует только фактическую потерю HP после барьеров и с учётом оставшегося HP; похищение ресурсов ограничено реально отнятым. После урона и немедленных смен состояния выполняется отражение, затем вампиризм. Отражение использует явно заданную базу `reflect_absorbed`, `reflect_hp_loss` или `reflect_incoming`, тип урона и защиту получателя; по умолчанию не вызывает отражение повторно, обычный вампиризм, крит или on_hit исходной атаки. Уже порождённый вампиризм может завершиться после incapacitated источника, если KB не требует active, но не после dead. Обычные sustained прекращаются сразу при 0 HP, последующее лечение их не восстанавливает.

## 4. Статусы, время, AP и очередь

### 4.1. Наложение и длительность — S1.1–S1.16

```text
P_status = B, если H=R=0
P_status = clamp(B+30*(H-R)/(H+R),0,100), иначе
H = status_hit; R = status_resistance; B = base chance конкретного эффекта KB
```

Иммунитет запрещает наложение независимо от P. Положительные эффекты на союзников по умолчанию не проходят состязательную проверку. `on_hit` требует попадания, в том числе с нулевым уроном; `on_damage` — реальной потери HP, а не поглощения барьером; `on_cast` — успешного применения способности. У вероятностного статуса отдельный сохранённый бросок.

`own_turn` отсчитывается по ходам источника, `target_turn` по ходам цели, `round` по границе раунда. DoT/HoT срабатывает в начале соответствующего хода, включая последний тик; наложение само не наносит мгновенный урон без отдельного компонента KB. Контроль действует до конца затронутого хода. Три тика яда означают три применения, не четыре. В одной фазе — время наложения, затем стабильный ID; каждый тик отдельно фиксирует последствия и смены состояния.

По умолчанию экземпляры разделены по источникам; повтор того же источника обновляет срок как `max(остаток,новый)`, не силу. KB явно разрешает `stack`, `independent`, `reject`, общий scope или `extend`. Для stack обязательны stack_max и stack_per_apply; стаки экземпляра по умолчанию имеют общий срок, обновляемый и при достижении максимума. Ноль стаков удаляет экземпляр. Контроль разных источников действует параллельно, длительности не суммируются.

Cleanse снимает негативные, dispel положительные: по умолчанию один разрешённый самый старый экземпляр, гарантированно после успешного применения. Массовость, категории, запреты, вероятность и частичное снятие стаков задаются KB. Частичное снятие не обновляет срок. Очищение не отменяет уже исполненные тики; иммунитет не удаляет действующий статус автоматически.

Scope: `combat`, `session`, `persistent`; combat прекращается после столкновения, session сохраняется в сессии, persistent пока не переносится автоматически между квестами. В мирной сцене ходовые таймеры не уменьшаются от постов. Смерть/выведение источника не снимают автономные эффекты автоматически.

### 4.2. Границы и поддержание — S1.13–S1.16, A1.4–A1.6, A1.44–A1.49

Новый раунд идемпотентно обновляет общий бюджет группы до 3 AP с действующими модификаторами, без переноса остатка. Начало соответствующего хода: обязательные тики в стабильном порядке, немедленные переходы состояния, затем поддержание и доступ к обычным действиям. События каждого существа независимы от открытия редактора владельцем. Кулдауны уменьшаются ровно на своих следующих границах начала хода: cooldown=2 доступен на втором следующем начале. Их нельзя уменьшать повторным HTTP-запросом.

Sustained оплачивается в начале хода источника, по выбранному игроком порядку либо FIFO. Каждый эффект оплачивается атомарно по всем ресурсам, AP только по явному KB. Не хватает ресурса — эффект прекращается без частичной оплаты; другие эффекты продолжают проверяться. Incapacitated/dead прекращают обычный sustained немедленно; иные виды контроля только по условиям KB. Уже оплаченные ресурсы не возвращаются. Посты в мирной сцене оплату не создают.

### 4.3. Действия и раунды — A1.1–A1.19, A1.46–A1.50

Персонаж, постоянные питомцы и обычные призывы используют общий бюджет 3 целых AP и один боевой пост за раунд; самостоятельные монстры GM имеют независимые бюджеты/ходы. Обычная атака, зелье, боевой предмет, смена оружия, передача предмета — по 1 AP. Способности — целая стоимость KB, по умолчанию 1; явные 0 AP требуют самостоятельных лимитов. Универсальной защитной стойки нет. Между боями экипировка меняется бесплатно.

Draft резервирует подготовку, но AP/ресурсы/расходники фактически оплачиваются атомарно при публикации, в том числе при промахе, сопротивлении, иммунитете и нулевом уроне. Все действия поста исполняются последовательно по виртуальному состоянию: восстановление первым действием позволяет оплатить последующее. Недопустимость любого действия блокирует весь пост без частичной механики и переброса.

Свободный порядок публикаций в раунде; порядок подтверждения сервером определяет event_sequence. Round turn roster фиксируется на начало раунда. Новые независимые участники обычно начинают со следующего; исключения только явные. Incapacitated не закрывает pending автоматически: восстановление позволяет действовать, пока ход открыт; resolved/passed/forfeited не открываются лечением. Обязательные границы обрабатываются один раз и при пропуске. Публикация закрывает ход resolved даже с остатком AP; seal его не закрывает. Неудачная публикация оставляет pending. Реакции разрешены после resolved без нового обычного хода.

### 4.4. Seal, квота, реакции — A1.14–A1.24, A1.57–A1.60

Незапечатанный draft свободно редактируется. Sealed фиксирует способность, параметры, цель, порядок и броски; дополнение допустимо в конец в рамках бюджета/квот. Отмена только с конца с сохранением истории и результатов. Отмена не расходует реальные AP/ресурсы, но не возвращает общую AP-квоту запечатанных попыток. Для 0 AP нужны обязательные лимиты KB. Объективный серверный конфликт восстанавливает только утраченные попытки отдельной идемпотентной аудируемой операцией без новых бросков.

Одна активная реакция на существо за раунд, отдельно от 3 AP; иные затраты KB. Фазы: on_targeted → before_hit → after_hit до урона → after_damage. Внутри — KB priority, время регистрации, стабильный ID. Условия и оплата перепроверяются непосредственно перед исполнением. Невозможная реакция пропускается без оплаты и лимита, проверяется следующая; выполненная расходует лимит и ресурс независимо от исхода. Активные реакции не порождают активные, пассивы имеют защиту повторов/циклов/глубины. Неразрешимый цикл блокирует весь commit.

При перехвате хранятся original_target и resolved_target; Hit/DEF/RES/барьеры фактической цели пересчитываются с теми же бросками. На атаку только одно успешное перенаправление, неуспешные не блокируют следующие. Обычный intercept только single_target. Массовая реакция требует KB, одна активация/стоимость/лимит, дополнительные затраты за цели только явно. Для multiple порядок выбора сохраняется, автоматические массовые цели имеют стабильный порядок. Цели после seal автоматически не заменяются.

## 6. Публикация, интерфейс, права и восстановление

Боевой пост — одно сообщение MyBB с двумя частями: неизменяемая карточка ACS в начале и редактируемая проза `posts.message`. Обычное редактирование/Quick Edit не вызывают резолвер. Narrative post не меняет механику, допустим до/после combat post и при paused по правилам MyBB. Удаление прозы или поста не уничтожает механический архив. A1.49–A1.52, A1.63.

Панель участников над постами внутри Adaptive Theme Framework: фильтры сторон, группировка питомцев, общий AP игроков, отдельный AP NPC; full/approximate/hidden только сервером. Детали ленивые. Sticky-строка ниже навигации без перекрытия meta-line; mobile — лента и адаптивные полноэкранные детали. Конструктор над существующим AdvancedEditor внутри одной формы, без второго SCEditor. Каталог с поиском и категориями Атака/Способности/Предметы/Экипировка/Тактика/Особые; известное недоступное действие отключено с безопасной причиной. Выбор self/single/multiple/all_allies/all_enemies/all_entities/area разрешает сервер. A1.53–A1.58, A1.87.

Preview до seal не генерирует случайность. Seal сохраняет броски/квоты; игрок явно подтверждает итоговую сводку перед публикацией. Изменившиеся зависимости требуют проверки и подтверждения обновлённой сводки с теми же случайными значениями, не молчаливого commit другого результата. Серверное автосохранение механики и прозы использует draft_version, локально резервируется проза; устаревшая вкладка не перезаписывает свежую. Восстановление само не публикует. A1.14–A1.16, A1.58–A1.60.

Каждый commit имеет submission_id. Повтор сначала читает результат: published возвращает прежний pid, доказанно не начатый допускает повтор тем же ключом, неопределённый — recovery_required без слепого повторения. Ошибки VALIDATION_ERROR/STATE_CONFLICT/PERMISSION_DENIED/DEPENDENCY_ERROR/INTERNAL_ERROR содержат безопасное сообщение/error_id; технические request_id/submission_id/phase доступны Diagnostics. Частичная механика недопустима. A1.60, A1.89.

Роли owner/gm/assistant_gm/player/observer дополняются глобальными правами MyBB/AF. Сервер проверяет сессию, форум, управление, делегирование, CSRF, версии и видимость каждой операции, включая JSON/CSV, агрегаты, список целей и уведомления. Критические correction/reward/permanent-sync/control/reopen требуют отдельных прав и причины. A1.41–A1.43, A1.63, A1.67–A1.68.

Синхронизация использует encounter_version/round_version/entity_version/draft_version/event_sequence. Нет постоянного агрессивного polling; транспорт AF/AAM — только при наличии реального контракта. Fallback: возврат во вкладку, открытие конструктора, seal/commit. AAM не источник механической истины. Сбой уведомлений и статистики не откатывает бой; опасная критическая интеграция без безопасного протокола блокируется. A1.61, A1.88–A1.93.

Отдельная реальная неоднозначность в пояснении S1.3: фраза о том, что статус с базой 0% «не должен случайно срабатывать», не следует из утверждённой относительной формулы при H>R. Единицы распределяются между компонентами методом наибольших остатков, равенства разрешаются по фиксированному порядку KB. <a id="s1-6"></a>

Для stack нужен обязательный stack_max; длительность обновляется как max(остаток, новая), без сложения. KB может явно задавать общий scope или extend.

<a id="s1-7"></a>

Источник, строка 2549. Утверждаю S1.7: одинаковые ограничения контроля от разных источников действуют параллельно, не складывают длительность, но сохраняют независимые экземпляры. Разные категории контроля могут сосуществовать; ограничения действий задаются KB.

<a id="s1-8"></a>
### S1.8 — Утверждённое правило

Источник, строка 2637. Утверждаю S1.8: по умолчанию стаки одного экземпляра статуса имеют общую длительность; успешное наложение добавляет stack_per_apply до обязательного stack_max, обновляет длительность по S1.6, даже если максимум достигнут. Сила определяется формулой KB; при нуле стаков статус удаляется.

<a id="s1-9"></a>
### S1.9 — Утверждённое правило

Источник, строка 2721. Утверждаю S1.9: cleanse снимает негативные статусы, dispel — положительные; по умолчанию выбирается один подходящий экземпляр, с автоматическим выбором самого старого. KB может задавать массовое снятие, категории, запреты и частичное удаление стаков. Частичное снятие не обновляет длительность; при нуле стаков статус удаляется.

<a id="s1-10"></a>
### S1.10 — Утверждённое правило

Источник, строка 2781. Утверждаю S1.10: cleanse и dispel по умолчанию гарантированно снимают подходящие разрешённые статусы при успешном применении способности. Вероятностная проверка, защита от снятия и специальные исключения задаются явно в KB. Бросок вероятностного очищения фиксируется до публикации; при неудаче статус не меняется.

<a id="s1-11"></a>
### S1.11 — Утверждённое правило

Источник, строка 2845. Утверждаю S1.11: статусы имеют scope combat/session/persistent. Combat заканчиваются после столкновения, session сохраняются между боями одной сессии, persistent пока не переносятся автоматически между квестами. Ходовые таймеры в мирной сцене не уменьшаются без специальных событий. 0 HP не считается автоматически окончательной смертью.

<a id="s1-12"></a>
### S1.12 — Утверждённое правило

Источник, строка 2906. Утверждаю S1.12: 0 HP означает incapacitated, не смерть. HP не опускается ниже нуля; обычные действия запрещены, лечение выше 0 HP возвращает active, если нет других ограничений. Dead — отдельное подтверждённое состояние, обычное лечение не воскрешает. Статусы не удаляются автоматически при выведении из строя или смерти источника; поддерживаемые эффекты регулируются KB.

<a id="s1-13"></a>
### S1.13 — Утверждённое правило

Источник, строка 2982. Утверждаю S1.13: поддерживаемые эффекты оплачиваются в начале хода источника; при нехватке ресурса эффект прекращается без частичной оплаты. AP расходуются на поддержание только при явном указании KB. Условия прерывания определяются эффектом, списания идемпотентны.

<a id="s1-14"></a>
### S1.14 — Утверждённое правило

Источник, строка 3051. Утверждаю S1.14: игрок выбирает порядок приоритета оплаты sustained-эффектов в начале хода; без выбора действует FIFO по времени наложения. Оплата каждого эффекта атомарна по всем ресурсам и AP, одноразова; неоплаченные эффекты прекращаются. В мирной сцене автоматических списаний за посты нет.

<a id="s1-15"></a>
### S1.15 — Утверждённое правило

Источник, строка 3124. Утверждаю S1.15: incapacitated и dead по умолчанию немедленно прекращают обычные sustained-эффекты. Оглушение, молчание, обездвиживание и прочий контроль прерывают только при явном условии KB. Автономные эффекты продолжаются независимо от состояния источника. Уже оплаченные ресурсы не возвращаются.

<a id="s1-16"></a>
### S1.16 — Утверждённое правило

Источник, строка 3209. Утверждаю S1.16: периодические эффекты одной фазы обрабатываются в порядке наложения, равенства разрешаются по стабильному ID. Каждый тик применяет и журналирует изменения состояния отдельно; очищение не отменяет уже произошедшие тики. Начало хода обрабатывается до поддержания и обычных действий.

D1.2 как отдельная финальная подпись в экспорте не выделен: коэффициент C=100 утверждён в D1 (строка 1085). D1.12 применяется в редакции D1.13, а не как второй алгоритм.

<a id="a1-1"></a>
### A1.1 — AP группы

Источник, строка 3276. Утверждаю A1.1: базовый бюджет 3 целых AP на группу игрока за раунд; у монстров GM независимые бюджеты. В редакторе AP резервируются без изменения боевого состояния, фактическое списание атомарно при публикации. Промах и неуспешная проверка расходуют AP; недопустимое действие останавливает публикацию без переброса.

<a id="a1-2"></a>
### A1.2 — Стоимость действий

Источник, строка 3355. Утверждаю A1.2: обычная атака, зелье, боевой предмет, смена оружия и передача предмета стоят по 1 AP; способности используют целую стоимость из KB, по умолчанию 1 AP, явные 0 AP допустимы только с ограничениями повторного применения. Универсальной защитной стойки нет; защита через способности. Бесплатная смена экипировки между боями сохраняется.

<a id="a1-3"></a>
### A1.3 — Оплата действий

Источник, строка 3439. Утверждаю A1.3: AP, ресурсы способностей и расходники оплачиваются при выполнении действия независимо от промаха, сопротивления, иммунитета или нулевого урона. Подготовка не списывает ресурсы; окончательное списание атомарно при публикации. Недопустимое действие останавливает публикацию без переброса.

<a id="a1-4"></a>
### A1.4 — Кулдауны

Источник, строка 3526. Утверждаю A1.4: кулдауны по умолчанию индивидуальны для существа и способности; KB может явно задавать общие группы перезарядки. Кулдаун запускается при выполнении независимо от результата, уменьшается в начале следующих ходов владельца; при cooldown=2 способность доступна на втором следующем начале хода. Повторные обращения не уменьшают кулдаун.

<a id="a1-5"></a>
### A1.5 — Scope кулдаунов и отдых

Источник, строка 3607. Утверждаю A1.5: кулдауны имеют scope combat/session; боевые сбрасываются после столкновения, сессионные сохраняются. Отдых оформляется явным событием ACS с настраиваемыми правилами KB для короткого и полноценного отдыха. Без события HP, ресурсы и статусы автоматически не восстанавливаются. Литературные посты не уменьшают кулдауны.

<a id="a1-6"></a>
### A1.6 — Обновление AP

Источник, строка 3682. Утверждаю A1.6: AP группы обновляются на границе каждого нового боевого раунда до базовых 3 с учётом действующих модификаторов; неиспользованные AP не переносятся. Поддержание способностей оплачивается из бюджета нового раунда. Обновление идемпотентно.

<a id="a1-7"></a>
### A1.7 — Восстановление отдыхом

Источник, строка 3766. Утверждаю A1.7: короткий отдых по умолчанию восстанавливает 25% максимального HP и ресурсов, допускающих восстановление отдыхом; полноценный отдых восстанавливает их до максимума. Конкретная сессия и KB могут переопределять параметры, сессионные статусы и кулдауны изменяются только по явным правилам. Отдых требует разрешённого события ACS, не восстанавливает расходники и не воскрешает dead.

<a id="a1-8"></a>
### A1.8 — Лимиты отдыха

Источник, строка 3790. Утверждаю A1.8: по умолчанию один короткий отдых между двумя боевыми столкновениями; полноценный отдых только по разрешению мастера. Лимиты и условия могут переопределяться через KB и настройки квеста. Каждое событие отдыха выполняется однократно.

<a id="a1-9"></a>
### A1.9 — Отдых питомцев

Источник, строка 3859. Утверждаю A1.9: одно событие отдыха распространяется на персонажа и присутствующих постоянных питомцев его группы. Временные призывы восстанавливаются только если сохраняются между боями и KB разрешает отдых. HP и ресурсы каждого существа восстанавливаются индивидуально по его максимумам. Отдых не создаёт исчезнувших призывов и не воскрешает dead.

<a id="a1-10"></a>
### A1.10 — События восстановления

Источник, строка 3939. Утверждаю A1.10: специальные события восстановления реализуются через session_event с правилами KB. По умолчанию их запускает мастер; KB может явно разрешить запуск игрокам. События имеют собственные лимиты и не расходуют лимит отдыха без явного правила. Применение атомарно, идемпотентно и журналируется. ACS изменяет только сессионное состояние, не исходный CharacterSheets.

<a id="a1-11"></a>
### A1.11 — Стоимость в HP

Источник, строка 4040. Утверждаю A1.11: HP может быть ресурсом способности. Оплата HP не является обычным уроном, не проходит через DEF/RES и барьеры, не активирует on_hit/on_damage. По умолчанию требуется оставить минимум 1 HP; KB может разрешить жертву до 0 HP, но не ниже имеющегося запаса. Жертвенная способность завершается, даже если оплата вызвала incapacitated; дальнейшие обычные действия запрещены. HP, AP и другие затраты списываются атомарно при публикации.

<a id="a1-12"></a>
### A1.12 — Вампиризм и конверсия

Источник, строка 4135. Утверждаю A1.12: вампиризм рассчитывается только от фактической потери HP цели после барьеров и с учётом оставшегося HP. Похищение ресурсов ограничено реально отнятым количеством. Лечение и восстановление не превышают текущие максимумы и не воскрешают dead. Преобразование ресурсов выполняется с предварительной проверкой стоимости по A1.11 и атомарным применением при публикации.

<a id="a1-13"></a>
### A1.13 — Порядок действий

Источник, строка 4233. Утверждаю A1.13: действия одного боевого поста выполняются последовательно в зафиксированном порядке. Результаты предыдущих действий, включая восстановление ресурсов, статусы и кулдауны, учитываются последующими. Персонаж и питомцы могут чередовать действия в рамках общего бюджета AP. Если любое действие становится недопустимым, публикация всего поста блокируется до исправления подготовки, без переброса уже запечатанных результатов. Атомарность всего поста сохраняется.

<a id="a1-14"></a>
### A1.14 — Draft и sealed

Источник, строка 4343. Утверждаю A1.14: до фиксации бросков draft можно свободно редактировать. После фиксации sealed нельзя менять цель, способность, параметры или порядок. Разрешена отмена только с конца очереди с сохранением запечатанных результатов и истории попыток; отмена не расходует AP и ресурсы и не даёт новых попыток переброса. Для серверных конфликтов предусмотрена отдельная журналируемая операция исправления без новых бросков.

<a id="a1-15"></a>
### A1.15 — Лимит попыток

Источник, строка 4451. Утверждаю A1.15: лимит запечатанных попыток привязан к бюджету AP хода; отменённые попытки не расходуют реальные AP, но не восстанавливают квоту подготовки. Для действий с 0 AP действует отдельный лимит KB. Объективный серверный конфликт допускает журналируемое, идемпотентное восстановление только утраченных попыток без перерасчёта уже запечатанных бросков.

<a id="a1-16"></a>
### A1.16 — Общая квота seal

Источник, строка 4542. Утверждаю A1.16: квота запечатывания выражается в AP и общая для всей группы управления, включая питомцев и призывов. Действие занимает квоту по своей стоимости AP, отмена квоту не возвращает. Активные способности за 0 AP имеют отдельные обязательные лимиты KB, их отмена не возвращает право на повторную попытку. Законные изменения бюджета AP в текущем раунде пересчитывают доступную квоту, не удаляя историю.

<a id="a1-17"></a>
### A1.17 — Бюджет реакций

Источник, строка 4645. Утверждаю A1.17: активные реакции используют отдельный бюджет — по одной реакции на каждое существо за раунд, без расходования основных 3 AP. Иные ресурсы оплачиваются согласно KB. Реакции настраиваются заранее, применяются при соответствующих событиях и не дают перебрасывать броски атак. Автоматические пассивные эффекты имеют собственные ограничения KB.

<a id="a1-18"></a>
### A1.18 — Фазы реакций

Источник, строка 4740. Утверждаю A1.18: реакции обрабатываются по фазам on_targeted, before_hit, after_hit (до урона), after_damage; внутри фазы — по приоритету KB, затем по времени регистрации и стабильному ID. Каждая реакция перепроверяет условия перед выполнением. Активные реакции не порождают другие активные реакции; пассивные эффекты защищены от повторного срабатывания на одном событии, циклов и чрезмерной вложенности. При обнаружении неразрешимого цикла публикация блокируется без изменения состояния и перебросов.

<a id="a1-19"></a>
### A1.19 — Оплата реакций

Источник, строка 4825. Утверждаю A1.19: активные реакции и пассивные срабатывания оплачиваются атомарно по актуальному состоянию. При нехватке ресурсов или невыполнении условий реакция пропускается без списаний; лимит активной реакции при этом не расходуется. ACS проверяет следующую подходящую реакцию в порядке A1.18. Выполненная реакция расходует ресурсы и лимит независимо от результата. Невозможность оплатить автоматическую реакцию не блокирует чужую атаку.

<a id="a1-20"></a>
### A1.20 — Перехват

Источник, строка 4920. Утверждаю A1.20: при перехвате ACS сохраняет original_target и фиксирует resolved_target. Все запечатанные броски остаются неизменными; попадание и урон пересчитываются по характеристикам фактической цели, включая Speed, DEF, RES, иммунитеты и барьеры. На одну атаку допускается только одно успешное перенаправление; неудачные попытки не блокируют последующие допустимые реакции. Реакции следующих фаз проверяются относительно актуальной цели. Обычный перехват доступен для single_target, массовые атаки требуют явных правил KB.

<a id="a1-21"></a>
### A1.21 — Массовые реакции

Источник, строка 5032. Утверждаю A1.21: массовые защитные реакции могут защищать несколько целей, если это явно предусмотрено KB. Одна активация расходует один лимит реакции и стандартную стоимость один раз; дополнительные затраты за цели возможны только по KB. Попадание, защита, барьеры и урон рассчитываются отдельно для каждой цели с сохранением запечатанных бросков. Обычный перехват не перенаправляет массовую атаку.

<a id="a1-22"></a>
### A1.22 — Общие барьеры

Источник, строка 5155. Утверждаю A1.22: KB поддерживает индивидуальные барьеры per_target и общие shared_pool. У shared_pool один общий запас прочности, который последовательно поглощает целочисленный урон в заранее зафиксированном порядке целей массовой атаки. Для per_target создаются отдельные запасы на каждого защищаемого участника. Состав защищаемых существ определяется KB; защита от двойного расхода общего запаса обязательна.

<a id="a1-23"></a>
### A1.23 — Очередь барьеров

Источник, строка 5240. Утверждаю A1.23: индивидуальные per_target и общие shared_pool барьеры участвуют в единой очереди поглощения урона. По умолчанию применяется FIFO по времени создания экземпляра, при равенстве — стабильный ID. KB может явно устанавливать barrier_priority, который учитывается перед FIFO. Для каждого компонента проверяется absorbs; разрушение shared_pool немедленно убирает защиту у всех целей. Общая прочность списывается атомарно.

<a id="a1-24"></a>
### A1.24 — Повторные барьеры

Источник, строка 5324. Утверждаю A1.24: повторное наложение одинакового барьера тем же источником в одной области по умолчанию заменяет старый экземпляр новым, с новой прочностью, длительностью и позицией FIFO. Операция restore восстанавливает прочность существующего барьера до его максимума, не меняет длительность и позицию и не оживляет разрушенный экземпляр. Stack разрешён только явно через KB с обязательным лимитом и независимыми экземплярами. Для shared_pool изменения относятся к одному общему запасу.

<a id="a1-25"></a>
### A1.25 — Отражение урона

Источник, строка 5428. Утверждаю A1.25: KB задаёт базу отражения reflect_absorbed, reflect_hp_loss или reflect_incoming и тип отражённого урона. Отражение проходит через соответствующие DEF/RES, иммунитеты и барьеры получателя; true обрабатывается по правилам истинного урона. Отражённый урон не вызывает повторного отражения, обычного вампиризма, критов или on_hit исходной атаки. Лечение восстанавливает HP, restore — только прочность барьера. Всё выполняется атомарно с журналированием.

<a id="a1-26"></a>
### A1.26 — Отражение и вампиризм

Источник, строка 5517. Утверждаю A1.26: после основного урона и немедленных переходов состояний обрабатывается отражение, затем вампиризм. Уже порождённый вампиризм может завершиться после incapacitated источника, если KB не требует его active-состояния; при dead обычное восстановление запрещено. Достижение 0 HP немедленно прерывает обычные sustained-эффекты, и последующее лечение не восстанавливает их автоматически. Все промежуточные события журналируются в одной атомарной операции.

<a id="a1-27"></a>
### A1.27 — Завершение столкновения

Источник, строка 5616. Утверждаю A1.27: после полного разрешения действия, реакций, отражения и вампиризма ACS проверяет условия завершения боя, определённые KB или настройками столкновения. При выполнении условий бой переходит в pending_resolution, новые боевые действия приостанавливаются. Мастер подтверждает результат либо разрешает допустимое продолжение. Взаимный incapacitated не означает автоматическую смерть или обязательную победу одной стороны. Подтверждение и любые корректировки журналируются; запечатанные броски и история урона не изменяются.

<a id="a1-28"></a>
### A1.28 — Капитуляция и отступление

Источник, строка 5718. Утверждаю A1.28: капитуляция — действие за 0 AP без броска, с отдельным состоянием surrendered. Побег отдельного существа стоит 1 AP, организованное отступление группы — 1 AP общего бюджета. Условия успеха, препятствия и эвакуация incapacitated определяются KB и правилами столкновения; автоматический перенос недееспособных существ запрещён. Состояния участия engaged/surrendered/escaped/withdrawn хранятся отдельно от active/incapacitated/dead. Завершение боя проходит через A1.27.

<a id="a1-29"></a>
### A1.29 — Проверка побега

Источник, строка 5820. Утверждаю A1.29: побег использует отдельную проверку Speed: P=clamp(60+30*(Speed беглеца−Speed преследователя)/(их сумма),10,90)%, при обеих скоростях 0 базовый шанс 60%. Преследователь — самый быстрый из способных препятствовать побегу. Без подходящих преследователей и других препятствий побег автоматический. Неудача расходует 1 AP, результат запечатывается. Организованное отступление за 1 AP проверяет подходящих участников индивидуально, возможен частичный успех. Ограничения и специальные эффекты — через KB.

<a id="a1-30"></a>
### A1.30 — Возвращение

Источник, строка 5917. Утверждаю A1.30: частичное отступление не выводит автоматически оставшихся питомцев и призывов из боя; они сохраняют общую группу управления и оставшийся бюджет AP. Вернуться можно через отдельное журналируемое событие rejoin_encounter по условиям KB и столкновения. Возвращение не восстанавливает AP, квоту запечатанных попыток, лимит реакций, ресурсы или боевые кулдауны. Временные призывы проверяют условия существования по KB.

<a id="a1-31"></a>
### A1.31 — Захват

Источник, строка 6029. Утверждаю A1.31: surrendered и captured — разные состояния участия, restrained — статус KB. Стандартный захват доступной сдавшейся или incapacitated цели стоит 1 AP при соблюдении условий KB; захват сопротивляющихся целей требует специальной механики KB. captured не изменяет HP, статусы, кулдауны, экипировку и инвентарь автоматически. Освобождение и побег из плена оформляются отдельными проверяемыми событиями, изменения атомарны и журналируются.

<a id="a1-32"></a>
### A1.32 — Custody

Источник, строка 6132. Утверждаю A1.32: конфискация предметов использует сессионный механизм custody и не изменяет собственника в AdvancedInventory. Изъятый предмет становится недоступен для использования и экипировки в соответствующем контексте, его бонусы удаляются из расчёта ACS. Освобождение пленника и возвращение вещей — отдельные операции. Окончательная передача собственности выполняется только через разрешённую операцию AdvancedInventory с учётом глобальных резервирований. Незавершённые custody-записи нельзя терять при закрытии сессии. Все изменения атомарны и журналируются.

<a id="a1-33"></a>
### A1.33 — Временное использование

Источник, строка 6229. Утверждаю A1.33: конфискованный предмет может временно использоваться хранителем только по явному разрешению KB или GM, без передачи собственности в AdvancedInventory. Предмет имеет одного активного пользователя внутри сессии, бонусы применяются только к нему. Custody изолировано между параллельными сессиями; глобальные ограничения передачи и резервирования сохраняются. Передача пленника другому хранителю не передаёт контроль над персонажем и не перемещает автоматически его вещи. Незавершённые записи хранения сохраняются в архиве сессии.

<a id="a1-34"></a>
### A1.34 — Loot pool

Источник, строка 6321. Утверждаю A1.34: ACS различает существующие трофеи, новую добычу loot и сюжетные награды reward. После подтверждения результата боя добыча создаётся в отдельном loot_pool, не зачисляется в AdvancedInventory автоматически. По умолчанию распределение подтверждает GM; KB и настройки квеста могут разрешать игрокам самостоятельно делить награды. Выдача через AdvancedInventory атомарна и идемпотентна, с защитой от дубликатов. Нераспределённые награды сохраняются после боя и закрытия сессии.

<a id="a1-35"></a>
### A1.35 — Генерация добычи

Источник, строка 6409. Утверждаю A1.35: KB поддерживает guaranteed, independent_roll и weighted_pool. Источниками добычи могут быть конкретные монстры и всё столкновение; условия получения задаются KB. Генерация выполняется один раз после подтверждения исхода, результаты и версия таблицы сохраняются неизменными. Повторные подтверждения, побеги и возвращения не создают новую добычу. Luck не изменяет шансы глобально, только при явном правиле KB. Изменения наград мастером оформляются отдельными журналируемыми событиями.

<a id="a1-36"></a>
### A1.36 — Распределение добычи

Источник, строка 6493. Утверждаю A1.36: распределение loot_pool поддерживает gm_assign по умолчанию, free_claim и need_greed по правилам KB/квеста. В need_greed приоритет имеют заявки need, затем greed; среди равноправных претендентов проводится однократная серверная жеребьёвка. Заявки изменяемы до закрытия, после закрытия неизменяемы. Выдача через AdvancedInventory атомарна и идемпотентна; при ошибке предмет остаётся зарезервирован за победителем без переброса. Повторное распределение возможно только отдельным журналируемым событием.

<a id="a1-37"></a>
### A1.37 — Непредметные награды

Источник, строка 6604. Утверждаю A1.37: непредметные награды ACS поддерживают experience, currency и другие типы через соответствующие обработчики AdvancedFunctionality/KB. По умолчанию получатели определяются по группам управления, без автоматического умножения наград на питомцев и призывов. Доступны режимы each, split_equal и manual; награды отдельным существам задаются явно через KB. Каждое начисление идемпотентно по награде, получателю и типу; частичные сбои не приводят к повторному начислению уже выданного. Активные снимки персонажей не пересчитываются автоматически после получения EXP.

<a id="a1-38"></a>
### A1.38 — Право на награды

Источник, строка 6705. Утверждаю A1.38: официальная регистрация группы управления в ACS до наступления условия завершения боя достаточна для базового участия в наградах; обязательного нанесения урона или выполненного действия нет. Питомцы и призывы учитываются в рамках своей группы без дублирования наград. Побег, капитуляция, incapacitated, dead и исход боя проверяются отдельно по условиям конкретной награды KB. Награды за индивидуальный вклад требуют подтверждённых событий. Вступление после завершения боя не даёт права на базовую добычу автоматически.

<a id="a1-39"></a>
### A1.39 — Закрытие сессии

Источник, строка 6824. Утверждаю A1.39: подтверждённые предметные и непредметные награды выдаются соответствующими системами по событиям, не ожидая закрытия квеста. Постоянные изменения характеристик и сюжетные последствия синхронизируются только отдельными разрешёнными операциями через контракты KB и соответствующих аддонов. Сессия проходит состояния active, pending_close, closed, archived; закрытие не удаляет журнал боя, незавершённый loot_pool, custody или обязательства синхронизации. Переносы идемпотентны и допускают безопасное восстановление после частичных сбоев. Боевые снимки других сессий автоматически не меняются.

<a id="a1-40"></a>
### A1.40 — Переоткрытие и исправления

Источник, строка 6907. Утверждаю A1.40: мастер может контролируемо переоткрыть closed-сессию через reopen_session, сохраняя все идентификаторы и неизменяемую историю. Переоткрытие не восстанавливает ресурсы, AP, кулдауны, квоты и не пересоздаёт награды; завершённые столкновения не возобновляются автоматически. Ошибки исправляются отдельными correction_event с проверкой возможностей принимающих аддонов, без прямого переписывания истории. Archived-сессии не возвращаются в обычную игру, но незавершённые обязательства можно безопасно разрешать. Все операции идемпотентны и журналируются.

<a id="a1-41"></a>
### A1.41 — Роли и права

Источник, строка 7041. Утверждаю A1.41: ACS использует сессионные роли owner, gm, assistant_gm, player, observer и отдельные глобальные права MyBB/AF. Для критических операций — исправлений, корректировки наград, изменения постоянных данных, передачи управления и переоткрытия — предусмотрены отдельные разрешения. Все действия проходят серверную проверку полномочий, принадлежности существ, состояния сессии, CSRF и версии данных. Защищённые операции требуют причины и журналируются. Администратор ACS может передать владение сессией другому пользователю без изменения её механической истории.

<a id="a1-42"></a>
### A1.42 — Контроллеры NPC

Источник, строка 7131. Утверждаю A1.42: ACS поддерживает controller_assignment для NPC и монстров с режимами exclusive, shared, gm_pool. Несколько мастеров могут готовить действия параллельно; публикация атомарно проверяет актуальные версии существа, цели и общих зависимостей, а также текущие права. Конфликты не допускают повторных бросков и обрабатываются по A1.15. Передача контроля не восстанавливает ресурсы и журналируется. GM не получает автоматического права действовать за персонажей игроков и их постоянных питомцев.

<a id="a1-43"></a>
### A1.43 — Делегирование

Источник, строка 7250. Утверждаю A1.43: ACS поддерживает сессионное control_delegation с указанием владельца, делегата, существ, полномочий и срока действия. По умолчанию делегирование предоставляет право на обычные боевые действия; использование расходников, смена экипировки, побег и капитуляция требуют отдельного разрешения. Передача собственности, изменение CharacterSheets и повторное делегирование запрещены. GM может назначить замену без текущего согласия владельца только по заранее согласованному правилу квеста или отдельному административному разрешению. Делегат использует те же AP, квоты и реакции, что и владелец; отзыв действует на будущие публикации. Всё журналируется.

<a id="a1-44"></a>
### A1.44 — Дедлайны и пропуски

Источник, строка 7333. Утверждаю A1.44: тайм-ауты ходов настраиваются отдельно для каждого столкновения и по умолчанию выключены. GM может выбрать уведомление без пропуска, автоматический timeout_pass или ручной gm_skip. Пропуск не создаёт защитных, атакующих или иных новых действий и не расходует неиспользованные AP; обязательные тики статусов и оплата sustained обрабатываются по ранее утверждённым правилам. Запечатанные черновики не публикуются автоматически. Паузы, дедлайны и пропуски журналируются, обработка идемпотентна и защищена от гонок с публикацией. Делегат и владелец разделяют один дедлайн группы.

<a id="a1-45"></a>
### A1.45 — Пауза

Источник, строка 7440. Утверждаю A1.45: ACS поддерживает paused как отдельное состояние столкновения. Во время паузы не допускаются новые механические публикации и запечатывание, не продвигаются раунды, статусы, sustained, кулдауны, AP и реакции; обычный литературный текст и незапечатанные черновики разрешены. Все дедлайны замораживаются с сохранением оставшегося времени, при возобновлении восстанавливаются. GM может отдельно продлевать сроки через extend_deadline. Уже запечатанные действия сохраняются, но повторно проверяются перед публикацией. Пауза, возобновление и изменение дедлайнов атомарны и журналируются. По умолчанию бой возобновляет мастер.

<a id="a1-46"></a>
### A1.46 — Свободный порядок ходов

Источник, строка 7542. Утверждаю A1.46: внутри раунда действует свободный порядок публикаций, без обязательной инициативы. По умолчанию призванные игроком существа входят в его control_group и используют оставшиеся общие AP без второго боевого поста. Самостоятельные NPC-призывы получают отдельный ход начиная со следующего раунда по A1.47, если KB не предусматривает строго ограниченный немедленный эффект on_spawn_effect. KB определяет лимиты количества призывов, длительность, поддержание, исчезновение и переход к независимости. Призыв не восстанавливает AP и не открывает закрытый ход. Создаваемые объекты работают по A1.71/A1.83 и не получают AP по умолчанию. Размещение проверяется по зонам и ограничениям KB. Создание, изменения и исчезновение фиксируются идемпотентными событиями с ключами source_event_id + spawn_index и атомарно связываются с публикацией.

### A1.85 — Превращения

Источник, строка 12526. Утверждаю A1.85: ACS поддерживает превращения через временный эффект transform без создания нового entity_id, смены группы управления или сброса AP. Knowledge Base определяет режим формы modifier, override или hybrid и отдельный слой характеристик, не изменяющий постоянные данные CharacterSheets. При изменении максимального HP сохраняется абсолютное текущее HP с ограничением новым максимумом; отдельный запас HP формы допускается только явным контрактом KB. Экипировка работает через retain, suppress или adapt без автоматического удаления и физического снятия предметов AdvancedInventory. Набор доступных способностей меняется по KB, но кулдауны и ресурсы не сбрасываются автоматически. Статусы используют persist, suppress, remove или recalculate; подготовленные действия проверяют требования формы при срабатывании без замены способности и перебросов. Поддерживаются одна primary_form и дополнительные form_modifier/cosmetic_form по правилам совместимости KB. Превращение и обратное превращение расходуют AP по KB, не открывают дополнительных ходов и журналируются.

<a id="a1-86"></a>
### A1.86 — Копирование и перенос эффектов

Источник, строка 12705. Утверждаю A1.86: ACS поддерживает универсальные операции copy_ability, steal_effect, dispel_effect, reflect_effect и absorb_effect через существующий серверный резолвер Knowledge Base. Копирование создаёт временный granted_ability с источником, сроком, числом использований, стоимостью и политикой параметров caster_stats, source_snapshot или custom без изменения постоянных способностей CharacterSheets. Эффекты могут рассеиваться, переноситься или дублироваться по разрешённым контрактам KB; перенос закрывает старый экземпляр и создаёт новый со связанной историей, не повторяя уже исполненные тики и разовые эффекты. Отражение выполняется как дочерний эффект исходного воздействия по общим фазам реакций, не расходует AP и ресурсы первоначального исполнителя повторно, не создаёт новый ход и по умолчанию не допускает повторного отражения; цепочки возможны только с явным лимитом KB. Поглощение использует существующие барьеры и ресурсы по порядку расчёта KB. Все операции учитывают права видимости, версии, идемпотентность, запечатанные результаты и неизменяемый журнал.

### A1.87 — Адаптивный интерфейс

Источник, строка 12885. Утверждаю A1.87: ACS использует единый адаптивный интерфейс внутри существующего showthread.php без отдельной мобильной страницы и второго боевого редактора. Desktop отображает компактную панель участников, карточки и конструктор над AdvancedEditor; mobile использует горизонтальную ленту участников, компактную sticky-панель, пошаговый конструктор и адаптивные полноэкранные детали. Все варианты используют один серверный черновик A1.59, одинаковый механизм запечатывания и публикации и существующий SCEditor/AdvancedEditor. Смена размера экрана не теряет механические действия или литературный текст. Журнал, детали, тяжёлые формы и GM-инструменты загружаются лениво по правам и контексту; стили изолированы от MyBB и Adaptive Theme Framework. Sticky-панель не перекрывает навигацию, meta-line и редактор. Интерфейс обеспечивает доступность клавиатуры, сенсорное управление и отсутствие раскрытия скрытых сведений.

<a id="a1-88"></a>
### A1.88 — Синхронизация

Источник, строка 13052. Утверждаю A1.88: ACS использует событийную синхронизацию с проверкой encounter_version, round_version, entity_version, draft_version и event_sequence, без постоянного агрессивного polling. При доступности общего транспорта AF/AAM обновления доставляются через него; при отсутствии соединения используются проверки при возвращении во вкладку, открытии конструктора и перед запечатыванием или публикацией. Сервер возвращает только разрешённые изменения, а клиент не раскрывает скрытых сведений и не перезаписывает выбранные действия, цели, литературный текст или запечатанные броски. При устаревшем черновике показывается конфликт с возможностью исправления незапечатанных действий без автоматического переназначения целей и перебросов. AAM остаётся каналом пользовательских уведомлений, а не источником механической истины. Потеря соединения не уничтожает черновик; публикация без серверной проверки запрещена, неизвестный результат отправки обрабатывается по A1.60. Все запросы проверяют права и версии, тяжёлые данные загружаются лениво.

<a id="a1-89"></a>
### A1.89 — Ошибки

Источник, строка 13237. Утверждаю A1.89: ACS использует структурированные категории VALIDATION_ERROR, STATE_CONFLICT, PERMISSION_DENIED, DEPENDENCY_ERROR, INTERNAL_ERROR и отдельное состояние RECOVERY_REQUIRED. Игрок получает безопасное понятное сообщение и уникальный error_id без внутренних SQL, PHP и скрытых боевых сведений. Техническая диагностика доступна уполномоченным администраторам в разделе Diagnostics A1.67 и связывается через request_id, submission_id, encounter_id, operation и phase. При ошибках до запечатывания механика не применяется, черновик сохраняется; после запечатывания результаты и квоты не пересоздаются. Публикация восстанавливается через проверку submission_id по A1.60: подтверждённая возвращает существующий pid, безопасно не начатая может повторяться с тем же ключом, неопределённая переводится в recovery_required без слепого повтора. Ошибки Knowledge Base и интеграций не допускают частично применённых эффектов; для нетранзакционных зависимостей необходим идемпотентный протокол согласования и восстановления либо блокировка опасной операции. Диагностика не переписывает журнал ACS, а исправления выполняются отдельными разрешёнными correction_event с причиной и аудитом. Логирование ограничено по объёму и не нагружает showthread.

<a id="a1-90"></a>
### A1.90 — Хранилище

Источник, строка 13512. Утверждаю A1.90: AdvancedCombatSystem использует модульную реляционную схему таблиц af_acs_* с префиксом MyBB и транзакционным хранением InnoDB. Отдельно хранятся сессии, столкновения, раунды, ходы, участники, контроллеры, актуальные состояния, снимки KB/CharacterSheets, эффекты, кулдауны, черновики, запечатанные действия и броски, submissions, связи с posts.pid, объекты окружения, зоны, осведомлённость и интеграционные операции. Подтверждённая история хранится в неизменяемых af_acs_events/event_details с уникальным event_sequence внутри столкновения; исправления являются отдельными событиями. Текущие таблицы служат материализованным представлением подтверждённой истории, а showthread читает их без пересчёта всего боя. Индексируемые идентификаторы, статусы и версии хранятся отдельными SQL-столбцами, сложные параметры и снимки KB — в версионированных JSON. Интеграции AF остаются владельцами постоянных данных, а ACS хранит боевые снимки и ссылки на внешние операции. Публикации используют submission_id, согласованные транзакции и блокировки, idempotent outbox для уведомлений и recovery_required для неопределённых внешних результатов. Миграции схемы версионируются, обычная деактивация не удаляет данные. Окончательный SQL DDL и число таблиц определим при составлении технического задания.

### A1.91 — Модули

Источник, строка 13746. Утверждаю A1.91: AdvancedCombatSystem реализуется как модульный аддон AdvancedFunctionality с разделением Bootstrap, Domain, Application, Infrastructure, Presentation и Administration. Регистрация хуков и минимальное определение контекста не загружают тяжёлый резолвер на обычном showthread.php; view, builder, seal, commit, GM и ACP загружают только необходимые модули. Все боевые механики используют единый серверный резолвер с режимами preview, seal и commit, без независимых способов применения урона или выполнения бросков. Контракты KB версионируются и снапшотируются, их изменение не переписывает запечатанную историю. Сервер централизованно проверяет управление, делегирование, полномочия GM и видимость данных. ACS не изменяет ядро MyBB, не создаёт второй AdvancedEditor, не подменяет постбит ATF и не дублирует обработчики публикации. Сбои некритичных интеграций не откатывают подтверждённый бой, критичные операции безопасно блокируются по A1.89.

### A1.92 — Производительность

Источник, строка 13960. Утверждаю A1.92: ACS использует контекстные режимы загрузки inactive, view и interactive, без подключения тяжёлого резолвера, интеграций и конструктора на обычном showthread.php. Ассеты подключаются через существующий manifest/af_frontend_asset_allowed, а builder, GM, журнал и подробные карточки загружаются лениво по контексту и полномочиям. Контракты Knowledge Base кэшируются по contract_id, версии и schema_version; боевое состояние хранится в материализованных SQL-таблицах и не заменяется недостоверным кэшем. Пользовательские представления фильтруются на сервере с учётом прав и осведомлённости, без утечки скрытых существ даже через агрегированные количества. Участники, статусы и связи загружаются пакетно без N+1-запросов; большие группы отображаются компактно, журнал и каталоги используют пагинацию. Для API предусмотрены ограничение частоты и размера ответов, для seal — утверждённые квоты, для публикации — идемпотентность. ACS не создаёт повторных инициализаций SCEditor, ATF и CharacterSheets или двойных подключений через AdvancedJSBundle. Производительность оценивается по TTFB, памяти PHP, SQL-запросам, JS payload и времени API; конкретные пороги устанавливаются после профилирования. Кэш не может обходить проверки актуального состояния, версий, ресурсов и серверных прав.

### A1.93 — Жизненный цикл аддона

Источник, строка 14179. Утверждаю A1.93: AdvancedCombatSystem использует независимые операции install, activate, deactivate, upgrade и uninstall. Обычная реактивация не пересоздаёт таблицы, не сбрасывает настройки, AP, раунды, журнал или черновики и не перезаписывает шаблоны Adaptive Theme Framework, AdvancedEditor и других аддонов. ACS регистрирует собственные шаблоны по версиям и использует согласованные точки расширения AF/MyBB без правок ядра. При установке и обновлении проверяются совместимость схемы и зависимости; критические механические операции блокируются при недоступности необходимых контрактов, а некритичные интеграции AAM и AdvancedStatistic не останавливают бой. Миграции выполняются последовательно, возобновляемо и с контролем фактического состояния схемы, без предположения о полном транзакционном откате DDL MySQL. Активные сессии, исторические события, запечатанные броски и версии контрактов KB сохраняются при обновлении. Деактивация отключает механические операции, но сохраняет данные и не освобождает внешние резервации без согласованной процедуры. Полное удаление данных ACS требует отдельного административного подтверждения и проверки незавершённых операций. ACP показывает состояние интеграций и ошибки совместимости. Перед релизом выполняется ограниченная целевая проверка установки, миграций, повторной активации, публикации и конфликтов с ATF, AdvancedEditor и Inventory без избыточного облачного тестирования.
