# AdvancedShop → AdvancedAppearance: постоянные слоты

Этап 6. MyBB 1.8.40 / PHP 8.5. Продажа ёмкости использует существующие Shop checkout, Balance и историю `af_shop_orders`; права хранятся в существующей `af_aa_slot_grants`.

## Обновление и настройка

1. Обновить файлы и выполнить upgrade/activate AdvancedAppearance **1.4.0**, затем AdvancedShop **1.1.0**.
2. В магазине с machine code `appearance_slots` / названием «Слоты оформления» открыть управление товарами. Указать цену/существующую валюту и включить товар «Дополнительный слот: Постбит».
3. Проверить бесплатную и максимальную ёмкость postbit в настройках Appearance.

Цена не задана в техническом задании. Миграция создаёт postbit-товар **выключенным**, с нулевой заготовкой цены; она не назначает стоимость и не начинает бесплатную раздачу. Повторная активация сохраняет цену, включение и существующие товары. Ссылка «Купить слот» в мастерской появляется только при наличии включённого товара, доступного конструктора и запаса до максимума.

Registry резервирует `postbit`, `profile`, `sheet`, `theme` с постоянными `source_ref_id` 1–4. Сейчас создание/продажа разрешены только для реализованного, разрешённого ACP конструктора `postbit`. Для остальных типов товар не создаётся; подстановка ref в HTTP/БД не обходит серверную проверку конструктора при покупке.

## Контракты и схема

- Отдельный `source_type=appearance_slot`, `kb_type=appearance_slot`, `kb_key=appearance_slot.postbit`. Старые `source_type=appearance` и `kb` сохраняются и проходят прежнюю выдачу Inventory.
- За единицу количества выдаётся `appearance_slot.{target} +1`. Это постоянное право, без Inventory-предмета, активации, пустого пресета или назначения стиля.
- Appearance: `af_aa_slot_product_registry()`, `af_aa_slot_assert_purchase(uid,target,qty)`, `af_aa_slot_grant_order_line(...)`, `af_aa_slot_revoke_order(...)`. Формулу и максимумы определяет только Appearance. Системный виртуальный пресет ёмкость не расходует.
- Shop сохраняет `slot_target`, `entitlement_key`, количество, цену и валюту в `items_json` заказа. Строка права получает UNIQUE `source_key=shop:{order_id}:{line_index}:{target}`. Исторические заказы без entitlement marker не переигрываются.
- Additive DDL только при install/activate: nullable `checkout_key CHAR(64)` в `af_shop_carts` и `af_shop_orders`, UNIQUE `(uid,checkout_key)` в orders. Старые строки остаются NULL. Таблицы Shop carts/cart_items/orders/slots переводятся в InnoDB при необходимости; данные не переписываются.
- Новая schema Gallery, Appearance, Inventory, MyBB users/posts не нужна. Используется существующая таблица Appearance grants из этапа 3.

## Покупка и повторы

Сервер выдаёт случайный checkout key текущей ревизии корзины. Add/update/очистка корзины меняют ключ. UI передаёт его вместе с существующим CSRF. Старые вызовы checkout без дополнительного поля сохраняют совместимость: используют текущую ревизию под блокировкой, повтор пустой корзины не оплачивается.

Checkout сериализуется по UID тем же MySQL advisory mutex, что CRUD Appearance. Внутри одной транзакции заново читаются корзина, товар и правила конструктора; суммарное количество всех строк одного target проверяется Appearance; блокируется строка Balance; создаётся paid order, списывается баланс существующим API, выдаётся право и очищается корзина. COMMIT подтверждает весь результат вместе. Ошибка выдачи откатывает заказ, платёж, ledger и право. Обновлённая вместимость доступна после COMMIT.

Повтор того же ключа возвращает прежний paid order. Повтор выдачи строки не добавляет capacity; UNIQUE source key остаётся дополнительной защитой. `af_advancedshop_replay_slot_order(orderId)` восстанавливает только права текущего владельца из подтверждённого order snapshot. HTTP grant/replay endpoints отсутствуют. Отменённый/refunded заказ не выдаётся.

Checkout проверяет InnoDB у участвующих Shop, Balance/ledger, Appearance grants и доступной Inventory-таблицы. Старое нетранзакционное хранилище Balance/Inventory требует отдельного перевода администратором до покупки; сервис отказывает до списания денег. Другие писатели Balance сохраняют свою прежнюю модель конкурентных обновлений; этот этап не переписывает экономику проекта.

## Возвраты

В Shop не было общего refund workflow. Добавлен серверный **manager-only** сервис `af_advancedshop_refund_slot_order(orderId)` для заказов, состоящих только из slot products. Он в одной транзакции возвращает исходные суммы по валютам через Balance с reason `shop_refund`, выключает права этого order и ставит статус `refunded`. Повтор — без повторного возврата. Публичного refund endpoint нет; сервис предназначен для доверенного административного обработчика.

Смешанные заказы с Inventory/готовыми пресетами этот сервис отклоняет: у них остаётся прежняя экономическая модель, автоматического удаления чужих типов покупок нет. Незавершённый checkout прав не создаёт.

Уменьшение capacity сохраняет все определения и активные назначения. При переполнении запрещены создание/клонирование до освобождения места или восстановления прав; существующие пресеты не удаляются. Исторический replay не включает отозванный grant.

## UI и проверки

Мастерская читает свежую capacity и URL конкретного включённого товара из server API; после возврата/фокуса страницы обновляет карточки. Shop success предлагает перейти в мастерскую. Это не клиентский счётчик. Экраны управления поддерживают отдельный source type и postbit +1, старые типы сохранены.

Целевая проверка: `tests/appearance_shop_slots_integration.php` на PHP 8.5.0 / MySQL 8.4, изолированная БД `appearance_test`, префикс `aa_test_`. Проверены миграция/повтор активации, покупка без Inventory, capacity/история, retry/grant replay, два параллельных checkout одного ключа, чужой order, независимость targets, недоступный редактор, максимум, нехватка денег, отказ CSRF, устаревшая корзина, отключённый товар, rollback после принудительной ошибки выдачи, повторный возврат, сохранение переполненных пресетов и назначения. Bootstrap общий с тестом personal presets, сами проверки этапа 3 повторно не запускаются. Production БД/цены и браузерное окружение форума не затрагивались.

Основные файлы: `advancedshop/appearance_slots.php`, интеграционные ветки `advancedshop.php`, Shop JS/шаблоны, `advancedappearance/slot_entitlements.php`, `personal.php`, `assets/studio.js` и manifests.
