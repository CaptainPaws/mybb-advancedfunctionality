# IC-INV-1 v1 — owner-side protocol (ACS-6.1.1)

Статус: **CONTRACT PREPARED / runtime BLOCKED**. Это уточнение IC-INV §6 и Architecture §5.5, а не готовый API. Аудит и условия допуска: [ACS-6.1.1](../design/acs/ACS_6_1_1_IMPLEMENTATION.md). Наличие схемы payload или SQL fixture не разрешает боевой расход. Старые writers не заменены и ещё обходят предлагаемую защиту.

## Authority и формат

AdvancedInventory единолично хранит qty, постоянный uid, экземпляры и глобальную доступность. KB определяет предмет; normalized_item — проверенный сервером pinned KB snapshot, не пользовательский JSON. ACS хранит reservation references, боевой комплект, использование и сессионный custody; mirror не является вторым балансом имущества. Reservation не уменьшает qty и не меняет uid.

[JSON Schema](ACS_INVENTORY_OWNER_REQUEST.schema.json) задаёт замкнутый envelope v1 для шести операций. Это серверный контракт, HTTP route не добавлен. Сигнатуры остаются reserve(key,owner_uid,item_id,qty,session_id,expected_inventory_version), consume(key,reservation_id,qty,expected_version), release(key,reservation_id,reason), transfer(key,item_id,qty,from_uid,to_uid,expected_versions), grant(key,recipient_uid,normalized_item,provenance), lookup(target_operation_key). Для единообразного read envelope lookup имеет собственный request key и payload.target_operation_key; lookup не создаёт receipt и не меняет целевую операцию.

actor.uid получают из authenticated runtime, authorization_ref ссылается на проверяемое серверное решение/делегирование. Это не bearer permission и не флаг validated=true. Проверяются свежие права на owner и конкретную операцию, ACS session/controller и отдельное разрешение расхода, срок/отзыв grants, native forum access и CSRF для HTTP mutations. Scope — system + immutable context_key (для ACS session_id); reserve.session_id обязан совпадать с context_key. Consume/release получают owner/item/session только из reservation и сверяют с текущим scope. Replay/lookup тоже авторизуются: знание key не открывает чужой результат. Session GM и право просмотра Inventory сами по себе не дают расходного права. Непроверенные transport actors не допускаются даже при валидном hash.

Qty — строго JSON integer 1..2147483647, без приведения строк/float/bool, округления и max(1,...). Reserve/consume/transfer используют payload.qty, grant — normalized_item.qty. У release/lookup qty отсутствует: release освобождает весь оставшийся резерв, lookup ничего не расходует. Item/uid соответствуют существующим INT; версии 1..2^53−1, exhaustion блокирует дальнейшую запись. Reservation ID возвращается как десятичная строка BIGINT. Дополнительно проверяются from_uid != to_uid, принадлежность item, JSON validity/canonical KB snapshot, KB hash/version и provenance; JSON Schema проверяет форму, а не эти права и связи. Стандарт JSON Schema считает 1.0 целым математически: parser дополнительно требует runtime integer (PHP is_int), как strict type checker fixture.

payload_hash = SHA-256 UTF-8 canonical JSON всего envelope **без operation_key и payload_hash**. Все object keys ASCII, сортируются bytewise; array order сохранён; пробелы отсутствуют; Unicode и slash не escape-ятся, control characters escape-ятся как JSON; U+2028/U+2029 сохраняются UTF-8 (PHP JSON_UNESCAPED_LINE_TERMINATORS); числа только целые, никаких floats, NaN, дубликатов ключей и скрытой Unicode normalization. snapshot_json — строка точных байтов проверенного KB JSON (не повторно сериализуется для сравнения stack). Actor, scope, operation, schema_version, qty, versions и provenance входят в hash. Авторизация перепроверяется при каждом вызове, authorization_ref не меняют на replay; новый grant не даёт права переписать старый intent. Hash пересчитывает owner, присланный hash без проверки не принимается.

## Состояния и durable result

Owner operations — общий журнал Inventory, не ACS. Глобальный binary/case-sensitive PRIMARY KEY(operation_key); namespaces acs:/shop:/inventory: выдаёт сервер, пользователь не выбирает чужой namespace. Одинаковые key + computed hash + исходный actor/scope возвращают сохранённый результат **до** проверки старых expected versions. Другой hash — IDEMPOTENCY_CONFLICT, исходный receipt неизменен. Сравнивают и canonical intent, чтобы не доверять одному переданному hash.

Одна owner InnoDB transaction на authoritative writer включает operation row, изменение имущества/reservation, versions и terminal result_json. Незавершённый journal insert не коммитится отдельно. Внутреннее executing существует только внутри tx; наружу возвращается только durable receipt после COMMIT. Business rejection (shortage, stale version, invalid state) фиксируется как rejected без изменения имущества. Ошибки аутентификации/формы до начала операции не создают чужих receipts. SQL failure откатывает tx; неизвестный COMMIT не считается rollback.

Receipt v1: schema_version, operation_key, operation_type, payload_hash, actor_uid, scope, status, code, external_ref, item_id, qty, inventory_versions (uid→before/after), reservation (id, remaining_qty, version, status) либо null, result_hash. Для transfer также destination_item_id; для grant — фактический созданный/объединённый item_id. Nullable item/ref/qty у rejected не подменяются фиктивными успехами. result_hash = SHA-256 canonical JSON receipt без result_hash. Stored result неизменен и не пересчитывается из текущего qty; частичное consume имеет собственный receipt, прежний reserve receipt остаётся прежним.

Статусы: reserve=prepared (резерв активен), consume/transfer/grant=committed, release=released, business refusal=rejected. Это **terminal outcome конкретной операции**, prepared не означает расход. Сама reservation: active с remaining_qty>0 → consumed/released с remaining_qty=0; partial consume остаётся active и повышает reservation_version. Release новой key уже terminal reservation возвращает released с code=ALREADY_TERMINAL и qty=0, без изменения versions. Consume terminal либо excessive qty — rejected. Inventory versions увеличиваются ровно на 1 у каждого реально изменённого owner, reservation_version — при изменении reservation. Initial reservation_version=1. No-op и rejected versions не повышают.

lookup читает primary writer и возвращает found + точный проверенный receipt, либо not_found. Недоступная БД/неподтверждённый readback означает unknown/recovery_required на coordinator, никогда not_found. По timeout caller сохраняет key/hash/intent и резерв; сначала lookup, затем при доказанном not_found повторяет **тот же** key/hash/intent. Если прежняя tx ещё выполняется, unique operation key/owner locks сериализуют повтор. Новую key, release по таймауту, новый loot winner и remove_item как fallback запрещены. Receipt и terminal reservation не удаляются при item deletion, session close, uninstall/deactivation или архивировании. GC только по отдельной политике с сохранением dedupe tombstone/lookup; этого PR её не вводит.

## Глобальная доступность и версия

`available_qty = af_advinv_items.qty - SUM(active reservations.remaining_qty)` по item_id **по всем sessions/systems**. Никакого session filter в сумме. Нулевые/отрицательные legacy qty, orphan reservation и отрицательная available — integrity error, не clamp. Не использовать cached reads, read replica или MySQL consistent snapshot, созданный до ожидания locks: после locks — current/locking read.

Предлагается owner guard `af_advinv_owner_state(uid PK, inventory_version)`. Версия owner-wide: меняется при grant/remove/sell/update/equip/metadata/reserve/consume/release/transfer. Это намеренное уточнение предложенного item-level inventory_version в Architecture §5.5: отдельная item version в этом варианте не требуется. Guard сериализует и создание нового stack, когда item row ещё отсутствует. Reserve.expected_inventory_version и transfer.expected_versions.from/to относятся к guards; consume.expected_version — reservation_version. Lookup возвращает сохранённые версии, а не обещание актуальности.

Все writers обязаны участвовать, включая staff/bulk/repair/migrations и CharacterSheets. Уменьшение/продажа/обычный remove/transfer разрешены лишь на qty <= available. Set qty не может опустить owned ниже reserved. Full delete запрещён при active reservation; чистит bindings атомарно только после проверки. При ненулевом reserved запрещены изменение identity/metadata, merge с заменой snapshot, смена owner и изменения постоянных bindings этого stack; также проверяется прежний item заменяемого slot. Более разрешительная equip policy требует отдельного доказательства; здесь выбрана консервативная блокировка. Equip сам не создаёт резерв и не расходует единицу. ACS session loadout/custody не пишут постоянные bindings и не меняют uid.

Consume уменьшает owned и remaining на одинаковое qty, так что чужие резервы сохраняются; при owned=0 требует отсутствия остальных active reservations и выполняет owner cleanup bindings в той же tx. Grant увеличивает qty/создаёт экземпляр, не меняя чужие резервы. Существующий stack matcher uid/entity/subtype/kb_type/kb_key + точный meta_json сохраняют; MD5 служит лишь кандидатом, проверяют реальные bytes, выбирают min(id) при legacy duplicates. При активном резерве нельзя перезаписывать title/icon/meta старого stack: такой grant создаёт отдельный stack либо отклоняется по согласованной policy. Максимальный итог qty — signed INT max, overflow отвергается. Transfer перемещает только свободные единицы, сохраняет source id для чужих reservations, назначает destination через owner matcher, возвращает оба ID. Полная передача/удаление зарезервированной строки запрещены.

## Lock order и transaction boundary

Целевой порядок для **всех** Inventory/Shop/CS mutations:

1. Собрать полный owner set до tx; `INSERT ... ON DUPLICATE KEY UPDATE uid=uid` guard rows по uid ASC и `SELECT ... FOR UPDATE` тех же guards по uid ASC. Отсутствующий recipient не обходится gap lock. Guard содержит только uid/version, не qty.
2. Claim/lock единственную operation_key; replay/hash conflict завершается здесь без новых effects.
3. Если операция включает Shop: cart по id → order по id → Balance rows по uid/currency → appearance grants в стабильном порядке. Inventory-only эти системы не вызывает. Эти locks берутся до item/reservation; Balance и appearance callbacks с независимым COMMIT недопустимы.
4. Inventory items по id ASC (source и destination), reservations по id ASC; binding tables: equipped затем support_slots, внутри uid + slot bytewise. Availability: SELECT id,remaining_qty по item_id/status=active FOR UPDATE, затем сумма в owner code под item lock; это current read, а не прежний consistent snapshot. New stack insert выполняется под owner guard. Bulk сначала собирает **все** owners/items/slots и сортирует, а не захватывает их по порядку HTTP input.
5. Записать mutation, CAS versions, receipt и COMMIT. На writer readback подтвердить outcome при потере acknowledgement.

Для consume/release до tx разрешён read-only discovery owner/item из reservation; после guard всё перечитывается и проверяется, discovery не является authority. Для retry key другого actor/scope сначала read-only authenticated receipt discovery; несовпадающий intent не захватывает произвольный owner из старого результата. Owner API не вызывает ACS и не берёт ACS locks. Будущий ACS caller либо завершает свои tx до owner call, либо доказывает joinable same-connection boundary с порядком ACS locks → owner guards; этот PR ни один вариант не подключает. Никаких SQL locks во время HTTP/native MyBB hooks.

Standalone owner owns BEGIN/COMMIT и отказывает при чужой tx; Shop потребуется явно joinable internal primitive без BEGIN/COMMIT, durable receipt виден лишь после outer COMMIT. Это ещё не реализовано. Нынешний Shop owner advisory lock `af_aa_owner_*` не заменяет guard: checkout сейчас cart→Balance→grant, а Inventory sell item→Balance. Оба пути требуют refactor перед допуском, простое добавление FOR UPDATE небезопасно. Если сохраняется advisory lock, он берётся перед всеми SQL locks у всех участников, по uid ASC, без inverse acquisition; иначе соответствующие Shop/Appearance entry points BLOCKED. DDL/bootstrap/migrations не выполняются внутри owner tx.

Deadlock/lock timeout — rollback **всей** tx и ограниченный retry с тем же key/intent только при доказанном rollback. Неизвестный COMMIT → lookup. Случайные данные/KB snapshot не пересобираются на retry. Продажа с Balance и удаление с Appearance отдельно требуют доказательства joinability/receipt side effects; наличие Inventory receipt не делает внешнюю валюту атомарной.

## Схема и допуск

[SQL proposal fixture](fixtures/ACS_INVENTORY_OWNER_PROPOSAL.sql) создаёт только owner tables и воспроизводимую базовую Inventory таблицу на disposable DB. Она не зарегистрирована в install/activate/ACS migrations. Это проверяемый эскиз, **не production migration**: runtime protocol ещё не доказан writers/locks/fault injection. FK на удаляемый item намеренно отсутствует; terminal receipts/reservations переживают его удаление. Active logical FK проверяет owner под locks.

Допуск требует: миграционный план actual installed schema/engines; полный перевод всех перечисленных writers; authoritative read/write connection, atomic receipt, races двух sessions и reserve-vs-sell/delete/grant/transfer, partial consume/release/replay/hash conflict, rollback/unknown-COMMIT lookup; запрет reset/uninstall при обязательствах; отдельный протокол ACS commit/owner acknowledgement. До этого IC-INV executable operations, боевой расход, loot grant, equipment и custody остаются **BLOCKED**. Схема сама этот статус не снимает.
